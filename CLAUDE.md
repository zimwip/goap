# GOAP — notes for contributors and agents

- **English is the project's official language.** All code, comments, docs, commit messages, and UI text must be in English.
- Architecture and concepts: `docs/architecture.md`. Keep it in sync with code changes.

## Mental model: who, why, how, what, with what

GOAP manages the whole scope of an enterprise. **Organisations work on the Domain to change it as their needs
require. The need is the intent of a Change; how they perform it is the Methodology; its actions say which tools
they use.** Every design decision starts by asking which of these questions it answers, and lives in that concept.

| Question | Concept | What it is | Where it lives |
|---|---|---|---|
| **WHO** | **Organisation** | Who acts, and the scope of responsibility. A hierarchy of units (`OrgUnit`, `part_of`); the default unit `ORG-DEFAULT` is the root of every unit. A unit holds changes, the adapters of its tools and its users; who may do what (`Policy` nodes, ADR 0020) lives here too; a user holds no role of its own but the `admin` flag, its roles are held on projects (ADR 0043). Mirrored by a hierarchy of **Project** (`ProjectUnit`, `project_part_of`, root `PROJ-ROOT`): what the organisation works on, identifying the methodologies that apply and so the roles they inherit (ADR 0035 §2, ADR 0039). A `Change` belongs to a project (`ProjectID`). | graph, `organisation` namespace |
| **WHY** | **Change** (intent) | The reason to act, and the blackboard of the execution: everything that modifies the graph goes through one. It has an intent, an owner unit, a methodology, and acts on one namespace. Agents and actions work on it. Pure questions about the world state need none. | `domain.Change` |
| **HOW** | **Methodology** | How a change is performed: goals, conditions, agents, actions, triggers. | graph, `methodology` namespace (`MethodologyVersion` + element nodes typed by the `methodology` meta-domain, ADR 0023) |
| ↳ | **Agent** | A broad task scope that needs planning and loops to be achieved (goap / utility / hybrid planner); may call sub-agents. | methodology |
| ↳ | **Action** | The smallest task, not splittable: preconditions, effects, cost. Kinds `llm`, `tool`, `human`, `builtin`, `script`. It states the tools (MCPs) it uses. | methodology |
| **WHAT** | **Domain** | What is being changed: node types, links, lifecycles, algorithms (`alm`, `organisation`, `platform`, ...). One domain per namespace; a type is referenced as `<namespace>@<NodeType>` (ADR 0012, 0013). The versioned graph is its content. | `domains/`, registry database (`domain_version`); each graph holds the published ones in memory (type catalogue) |
| **WITH WHAT** | **MCP, Connector, Adapter** | **MCP**: the generic usage of a tool by an LLM (`platform` namespace). **Connector**: the driver of a real service, a separate service that registers itself. **Adapter**: the code that implements the tools an MCP expects with the operations a connector exposes. It is an `AdapterDef` node of the `platform` namespace (usage `adapter`, template generated from the MCP and the connector), changed through a Change; a unit holds an *instance* with its parameter values (secrets as references), where organisation, MCP and connector converge (`Adapter` node, `organisation` namespace, owned by the unit: the owner of its version, ADR 0054). | graph + connector registry (MCP hub) |

Design rules that follow, to keep the whole consistent:

1. **Keep the concepts independent; couple only at the designated meeting points.** A methodology knows no
   organisation and no connector (it names MCPs; it references the types of domains, `alm@Requirement`). An MCP knows no connector
   and no adapter. A connector knows no MCP and no organisation. A domain knows no methodology. The **Adapter** is
   where organisation, MCP and connector meet; the **Assignment** (`organisation@Assignment`, ADR 0039) is where
   organisation and project meet, carrying the roles a unit or user locally holds on a project; the **Change** is
   where who, why, how and what meet at run time.
2. **Every modification is a Change.** No write to the graph outside one (the direct-write endpoints are for
   seeding and non-controlled nodes only), and every change names its intent (why), its holding unit (who), its
   methodology (how) and its namespace (what).
3. **Responsibility flows down the organisation.** Anything an organisation provides (adapters today, policies and
   quotas tomorrow) is resolved from the unit holding the change, then its ancestors, then `ORG-DEFAULT`: the nearest
   wins. Units share an MCP and a connector with different scopes (same file access, different root directory).
4. **What describes the enterprise is graph data, changed through changes** (organisation, adapters, MCPs,
   methodologies): versioned, reviewable, journaled. The exceptions: the domains, which define the graph itself (the
   registry versions them in its database, each graph holds them in memory, ADR 0023), service configuration and
   runtime registrations (a connector announcing itself and its liveness).
5. **What is available comes from who.** An action is schedulable only where the unit holding the change resolves the
   MCPs it declares (`mcps:`); an agent may declare MCPs for its llm / script actions. ABAC decides what a principal
   may do; adapters decide what the organisation can reach.
6. **Agents plan, actions execute.** An action does one thing; anything that needs a loop, a choice or planning is an
   agent over smaller actions.
7. **Library and instance.** Whatever is reusable across organisations is written once in the domain library (an
   algorithm with declared parameters, ADR 0018) and instantiated where it is used with parameter values: an adapter
   is a definition (`AdapterDef`), and each unit gives it its own scope (same adapter, another root directory).
8. **Adding a capability**: name the question it answers, put it in that concept, and cross concepts only at the
   meeting points above. Adding a real service is a new connector (a service that registers itself), never a change to
   the platform.

## Working notes

- Go module `github.com/zimwip/goap`; core logic in `pkg/` (no infra deps), services in `internal/` + `cmd/`.
- Contracts: `proto/` → `make generate` (buf) → `gen/` (committed, never edit by hand).
- Tests: `make test`; PostgreSQL-backed tests (graph) run when `GOAP_TEST_PG_DSN` is set (`internal/pgtest`); SQLite variants always run.
- Storage has two SQL dialects: PostgreSQL (`migrations/`) and SQLite for the local mode (`migrations_sqlite/`, `make devlocal`, ADR 0010); schema changes go to both, and `TestSchemasAligned` (`internal/sqlschematest`, in `pkg/graph`, `credsvc`, `mcpsvc`, `modelgw`, `prefssvc`, `registrysvc`) fails on any difference of tables, columns, defaults, keys, constraints or indexes (ADR 0074). A graph query both repositories run is written once in `pkg/graph/sqlbuild.go` (`dialect` methods returning the text and arguments; a new query goes there, with its text per dialect in `sqlbuild_test.go`); what stays in `postgres.go` / `sqlite.go` is the executor, the scanning and the encodings. `make test-pg` runs every test against PostgreSQL (a throw-away `pgvector/pgvector:pg17` container unless `GOAP_TEST_PG_DSN` is set; there is no CI configuration in the repository, so run it before touching `postgres.go` or a `migrations/` file).
- `make lint` must pass (go vet + gofmt).
- `make.ps1` (and its `make.cmd` launcher) is the Windows twin of the `Makefile`: the same targets doing the same things (`devlocal` runs air with the build settings of `.air.toml` given on the command line, `.air.toml` being written for a POSIX shell); change both together.
- Example methodologies use the domain of `domains/` (`alm`) and the built-in `organisation` and `platform` (loaded in tests with `methodology.LoadFile`). `methodologies/examples/` (`impact-analysis`, `test-design`) is exercised by `pkg/methodology`, `pkg/engine` and registry tests and is not seeded at start (the registry seeds the `*.yaml` directly under `methodologies/`); `methodologies/sdlc.yaml` (ALM domain, demo data of `internal/devseed`) by `pkg/engine/sdlc_test.go`.
- One platform bootstrap (ADR 0071): every composition (`goap-dev`, `cmd/graph`) seeds through `graphsvc.Boot(ctx, g, Options)` — `Graph.Bootstrap`, `SeedAccess`, `SeedBuiltins`, `SeedModels`, then `Options.Dev` — never by calling the seeds itself (`TestCompositionsUseBoot`). Contract: the caller sets the graph hooks and loads the type catalogue first (`Options.RequireHooks` panics without the access hooks; without a guardian / `Lifecycles`, i.e. no registry in process, Boot logs one warning), the registry seeds the methodologies after. Development and demo data is separate (`internal/devseed`: `Demo`, `DocumentRepository`, `LocalFS` for `GOAP_DEV_FS_ROOT`): `goap-dev` passes it as `Options.Dev`, `cmd/graph` only with `GOAP_GRAPH_SEED=demo`; `SeedDefaults` no longer exists. Platform services take their identity from `authz.System(name, roles...)`.
- Versioning rule of the graph: outgoing links belong to the source node version (see `pkg/graph/apply.go`).
- Structures, bootstrap, guard (ADR 0054): a domain tags the node type building the organisation and the one building the projects (`structure: {kind, parent, root, selfParent, bootstrap}` on a node type: `bootstrap` gives the root's initial properties; one per kind across the domains, the built-in organisation domain tags `OrgUnit` / `ProjectUnit`; `TypeCatalog.Structure` / `IsA`, `Graph.Structure`; untyped graph: the catalogue of the built-in domains, `typecat.Builtin()`; ADR 0069: `pkg/graph` and `pkg/domain` name no structure, no root key, `pkg/layering` `TestCoreNamesNoStructure`; the constants of the built-in organisation are `access.DefaultOrg` / `DefaultProject` / `NodeTypeOrgUnit`..., for seeds and tests only). `Graph.Bootstrap` creates the roots the structures declare (`ORG-DEFAULT` and `PROJ-ROOT`) in one transaction and one applied change (services run it at start before any seed; `CreateChange` runs it too). `graph.New` wraps every repository transaction in the guard (`pkg/graph/guard.go`): every node version / link / branch membership (`JoinBranch` takes a change) / node origin names an existing change, every version has an owner unit (`Node.Owner`, stamped from the previous version, else the change's unit; moved only by `NodeUpdate.Owner` / `NodeEdit.Owner`) and every node a project (`Node.Project`, the change's at its first version, never changes), every baseline the result of a change (ADR 0056: the state before a namespace's first change is the empty baseline id, `""`, which nothing stores; `Baseline("")` / `BranchHead` read it), every change a unit and a project (`scopeChange`: the parent's, else the root unit for the unit; the project is never defaulted, a root change naming none is refused with `ErrInvalid`, ADR 0091), checked at the end of the transaction like deferred foreign keys; never bypass it (fixtures write through a change too, `seedNode`). The schema repeats it (`NOT NULL` foreign keys, deferred for the bootstrap; the schema started from zero, `0001_schema.sql`). There is no `organisation@owner` link: ownership is the version's owner (`SplitByOwner`, the adapters of a unit). The services reading the organisation (`pkg/access`, `internal/mcpsvc`) never name its types: they ask the graph for its structures (`Graph.Structures` / RPC `GetStructures`, `domain.Structures`: a list of structures with the types of each, `Organisation()` / `Project()`, a `User` being a unit; both structures live in one namespace, a platform constraint checked by `typecat`) and build their snapshots from them; the walk up a hierarchy is one resolver, `domain.Hierarchy` (`Structures.Hierarchy(kind, nodes, links)`, `Chain(key)`: self first, root last, cycle-safe), used by `access.Snapshot`, `mcpsvc.Snapshot` and the `goap-admin` listings (ADR 0068).
- Change lifecycle and gates (ADR 0058): a change may follow a domain lifecycle named by `Methodology.Lifecycle` (`Change.Lifecycle` / `State`, orthogonal to `ChangeStatus`; resolved through `graph.ChangeLifecycles`, implemented by `registrysvc.Service`, wired in `goap-dev`). `Graph.TransitionChange` checks the transition, `Graph.ChangeAuthorizer` (`change:transition`) and the CEL guard in the condition environment (`condition.CheckGuard`: `change`, `decisionPoints`, `world`); a gate is a guard requiring a decided decision point (`change.decision`, consumed by the move) and the `done` conditions of the steps of the state being left, no checklist of its own. A step is tied to a state by `pre: {"state:<name>": true}` (generated condition). The move is a `KindTransition` fact (written only by `TransitionChange`); leaving a state freezes the impacts whose draft was started in it (the checkout and the edits refuse), going back sets later ones to `proposed`; landing stays at the end (commit/apply need a final state). Keep the platform generic: states and gates are use-case level (domains, methodologies). Web: the change tab lists the transitions out of the state (`ChangeTransitions.svelte`, `web/src/lib/changeTransition.ts`, `graph.transitionChange`) and the assistant has `transition_change` (write, no second dialog). Not yet: engine builtin, `sdlc` lifecycle.
- Baselines and tags (ADR 0056): a baseline is the state a change leaves (`Baseline.ChangeID` mandatory), the first change of a namespace starts from the empty state (`BaselineID ""`, `change.baseline_id` nullable); a name is a `domain.Tag` on the change that left the state (`Graph.TagChange`, not unique: several changes may carry one name); there is no `CreateBaseline`. A change is applied in two steps: `CommitChange` validates it, writes the versions from its drafts (ADR 0079) and records its state on its own branch (baseline `Kind` `commit`, one `landed` event per impact, status `committed`), `IntegrateChange` integrates it into the branch it forked from (`fast-forward`: joins; `merge`: a merge change with its own `landed` events; status `applied`; conflicts leave it `committed`, the former `merge_pending`); `Apply` is both. A change is its branch (given at commit when it has none). A baseline's state is derived from what its change did (`landed` events, or the versions joined for a fast-forward), so only every `MaterializeEvery`-th baseline of a chain stores its entries (`Baseline.Gap` 0, `GOAP_MATERIALIZE_EVERY`, 1: all) and the others are a header, replayed and cached by the guard (`pkg/graph/state.go`; reads through the guard always hold the nodes, `Graph.Materialize` stores one). Run the suites with `GOAP_MATERIALIZE_EVERY=1`, `3` and `100000` after touching baselines: `checkStates` replays every baseline. `Apply`'s `baselineName` tags the change when it differs from its title. The check of the change impacts is `walkChangeImpacts` (properties, `walkTransitions`) then `settleChangeImpacts` (landing gate, the refusal of nodes left in a state that cannot land (ADR 0078), `checkTransition`, `runActions`; ADR 0072); `walkTransitions` follows the in-place moves recorded in the log of the change that wrote a version (ADR 0077).
- Drafts and versions at landing (ADR 0079; ADR 0076 checkout, ADR 0077 naming, merge and split, ADR 0078 landable states): a node has **no version during a change**. Every node write names a change (no `CreateObject`, no change-less write); `Graph.ImpactNodeCreate` / `ImpactNodeCheckout` give the node a **draft** per change impact and flow (derived from the change log, not stored: `domain.FoldDrafts`, read through `Graph.drafts`, a per-change cache validated by the log's last seq, `pkg/graph/draftcache.go`; `domain.Draft`: node id allocated at `created`, key, type, state, owner, properties, origins, `Base` = the version checked out from, outgoing links to an exact version or to a draft reference), once per change and flow (`graph.IsWorking`; a second checkout is `ErrConflict`, a child flow copies the parent flow's draft, `forkDraft`), and the impact's post is the **draft reference** `NodeRef{ID, Version: 0}` (`NodeRef.IsDraft`, `ChangeImpact.Drafted`; a draft reference is read through the change: `Graph.ChangeNodeView` / `ChangeNode`, `GetNode` with `change_id`, the blackboard and `ChangeView` hydrate it under that key, `draftReader` in `pkg/graph/draft.go`). `ImpactNodeUpdate` (props, owner) and `ImpactLinkCreate` / `ImpactLinkUpdate` / `ImpactLinkDelete` edit the draft (an `updated` event with the patch); the drafts are written only through `Graph.emit` (ADR 0029), by `domain.ApplyDraftEvent` over the events (`created` / `checkedOut` carry the initial `Draft`, `updated` / `transitioned` patches, `cancelled` / `withdrawn` / `landed` drop it; an adoption installs the flow's drafts on the main flow with `transitioned` events carrying a `Draft`), and `domain.FoldDrafts` rebuilds them from the log (`checkImpactLogs` replays every change on both repositories). **Reviews are always explicit**: an edit, a transition or a link edit never reviews (the bulk system paths `Graph.Commit` / `CommitEdits`, seeds, `EnsureUser` and `graphtest` review as the system principal: not user edits); an accepted review is the gate of what a version must satisfy, run on the draft (`checkAccepted` → `checkDraft`: attributes, validators, required links, link attributes, origins) and writes nothing; an edit after it sends it back to `proposed` (`editedAgain`). `ImpactNodeTransition` sets the state of the draft (`transitioned` event, patch `{"state": {from, to}}` and the properties its actions set; a node with no draft is checked out first, keeping the review; the CEL guard sees `node`, `change`, `impact` and `draft`, `guard.Guard.Check`); `ImpactNodeCancel` drops a draft (a creation cancelled removes its impact), `WithdrawImpact` takes an impact out of the change; a rejected impact keeps its draft (`ReopenImpacts` reopens rejected ones too). **Landing** (`CommitChange`, so `Apply`; `prepareChangeImpacts`) validates every draft again and **writes the versions** from the drafts in the commit transaction (`writeVersion`: the next number, `Parents` = the version checked out from, owner, origins, comment = last review comment, then the links, a draft reference or the version a draft was checked out from resolved to the version this landing writes for the node), on the change's own branch: no `node_version` row existed before, a version is immutable once written (the guard accepts links only for a version written in the transaction; `Tx` has no edit, freeze or drop of a version), the `landed` events then name the versions (the impact's post becomes the landed ref), node index events are published for them. A draft equal to its base still lands a version of its own. A node whose branch head moved since the draft was checked out is a conflict at landing (no longer a sub-change's doing: ADR 0081). Branches, `IntegrateChange` (fast-forward / 3-way merge) and baselines are unchanged: the commit step is where versions appear. The lifecycle phases of ADR 0058 follow the events that start a draft (`ImpactEvent.StartsDraft`), `walkTransitions` replays the recorded moves of a draft. Flows keep no branch: a flow's drafts are its own rows, `seenDrafts` / `DraftSeenBy` give what a flow sees (the innermost draft of its chain, the stale runs of ADR 0025 left out); adopting a flow (`adoptNodes`) installs its drafts on the main flow (a conflict when the main flow's moved on since) and resets the main drafts the stale runs wrote. A node is never deleted: removing a child is a modification of its parent; a node no parent holds is retired by its lifecycle (`config`: `active` / `retired`, on the MCPs, adapter definitions and model entries of `platform`, the adapters, policies and assignments of `organisation`; `access.InForce` leaves retired nodes out of the access and hub snapshots; `CommitEdits`' `state` retires, and restores a retired node in the same change as its edits; `Graph.Commit` moves a node with a draft to its state, then accepts it: a created user is one version). Edits are allowed in any state; a lifecycle state may be flagged `notLandable` (ADR 0078, `Lifecycle.Landable`: default landable) and a change lands only when each node ends in a landable state (`Lifecycle.Issues`: a not landable state must reach a landable one, a final state is landable). `graphtest` lands fixtures through these operations (`Import`, `Edit`, `Project`, `Unit`).
- Merge and split (ADR 0077, "Merge and split"): a node is never retired by one; merging A and B into C is a modification of their parents (nodes holding a `compose: true` link to them): the parent's draft loses the links to the sources and gains one to the new node (`Graph.ImpactNodeMerge` / `ImpactNodeSplit`, `pkg/graph/restructure.go`, one transaction over `resolve`; `TypeCatalog.Composes`), the sources' impacts carry `via` = the parent's impact, other links to a merged source follow it and ones to a split source are returned as suspect. The successor's draft records its origins, written to `Node.Origins` of its first version at landing (a `node_version.origins` column, `Graph.DerivedNodes` / `sqlDerivedNodes`, `patch.origins` of the `created` event, PROV `wasDerivedFrom`); `checkOrigins` holds its review and landing until the impacts of its origins are accepted. `MergeInput.Gate` carries the `adminOnly` gate over the parents it finds. Same names in the RPCs, `engine.GraphPort`, the DSL (`ctx.impactNodeMerge` / `impactNodeSplit`), the `goap-change` tools `merge` / `split` and `web/src/lib/api/graph.ts`.
- Sub-changes land in their parent (ADR 0081, superseding ADR 0016 §3-4): a sub-change (`Change.ParentID`) writes no version and no baseline. It sees its parents' main-flow drafts (`Graph.inheritedDrafts`, read by `draftReader`, `ChangeView`, `resolve`, link targets); its checkout of a node a parent holds a draft of copies it (`inheritDraft`, `Draft.Inherited` = `{change, impact, seq}` of the parent's log), a node a parent creates is taken as a `created` impact of the same node (`work.takes`). `CommitChange` of a sub-change (`commitSubTx`) checks the drafts as versions (`checkDraft`, origins, the landing gate on `subLandingBlackboard`) and writes nothing; `IntegrateChange` (`integrateSub`) installs each accepted draft in the parent's main flow (`transitioned` with `Draft` on the parent's impact of the node, else `proposed` + `checkedOut` / `created`, patch `{"integrated": {change, impact}}`, then a `reviewed` accepted carrying the sub-change's reviewer and comment), and writes `integrated` (`ImpactEvent.Into`, drops the draft) in the sub-change's log; the sub-change is `applied`, its branch closed. The integration is a fast-forward (ADR 0082): a draft is **behind** (`parentState.behind`: the parent changed its draft after `Inherited.Seq`, drafted a node the sub-change took from the stored version, or rejected / withdrew it) and `IntegrateChange` refuses (no `Resolution` for a sub-change). `Graph.RebaseChange` (`pkg/graph/rebase.go`) merges each draft behind three-way (`domain.MergeDrafts`: per property, owner, state, link by type + target node; base = the draft it was copied from, folded from that log up to `Inherited.Seq`, else the stored `Base`; `pkg/domain/draftmerge.go`), installs the result by a `transitioned` event carrying the `Draft` and `Patch {"rebased": {change, seq}, "conflicts": [...]}` (`props.<k>`, `owner`, `state`, `link:<type>:<node>`, `node` when the parent rejected or withdrew it; ours kept), and sends a changed impact's review back to `proposed`. Conflicts left are `domain.PendingConflicts` (an edit of the field settles it, `Graph.ImpactNodeResolve` keeps ours for all; `ImpactNodeCancel` / `WithdrawImpact` takes the parent's); an impact with conflicts cannot be accepted (`checkSettled` in `reviewTx`). `Apply` of a sub-change rebases first in its own transaction (`rebaseFirst`) and stops with `ErrConflict` when the rebase changed a draft. RPCs `RebaseChange`, `ImpactNodeResolve`, `GetRebaseState` (`Graph.RebaseState`: impacts behind, conflicts left), `graphsvc.Client`; web `SubChangeSync.svelte` on the change overview (`web/src/lib/rebase.ts` names the conflicts) and `SubChangeHistory.svelte` in its Changes pane (the family as a `HistoryGraph`: a lane per change, the fork / rebase / integration edges, `web/src/lib/subChangeHistory.ts`). The parent lands the integrated drafts as its own.
- Versions and branches (ADR 0032): `node_version.branch` is the branch a version was written on and never changes; a merge that lands a version as is makes it join the target (`Tx.JoinBranch`, `node_branch`), only a node changed on both sides gets a merge version. Ask "is it on branch X" with `LatestOn` / `Node.On`, not the label. Baselines are stored as deltas from their parent with checkpoints (`pkg/graph/baselinedelta.go`); callers still pass and get whole maps.
- Options (ADR 0009 §3, ADR 0032 §6): an option is a flow opened as a hypothesis (`pkg/graph/option.go`); the change's active option is where every graph call that names no flow goes (`Change.ResolveFlow` at the public entry points: `ProposeImpact`, the node operations of ADR 0076, `ImpactNodeReviewOn`, `AddItems`, `BlackboardIn`, `ValidateBoard`, `ChangeView`, `ChangeGraph`); `domain.MainFlow` ("main") names the main flow explicitly, internal code keeps passing "" for it. A flow keeps the mechanism only (ADR 0067): `Parent`, `ForkAfter`, the stale items, `StaleRuns` (opaque producer ids; the graph keeps the join / supersede rule over them) and `Origin` (an opaque record the opener owns, never read by the graph: the engine writes `{step, execution, process, reason}` for a relaunch); `OpenFlowRequest.Items` are written on the new flow at its creation (the engine's guidance artifact, `engine.GuidanceType`); `pkg/layering` keeps the core free of that vocabulary. Two flows are compared impact by impact by `Graph.DiffFlows` (ADR 0083: added / removed / modified, identical counted, `domain.DiffShapes` the pure attribute-level diff), shown by the Compare & decide dialog opened from the scope bar (`CompareDialog.svelte`, logic in `web/src/lib/flowDiff.ts`); `CompareOptions` only serves the `goap-change` tool.
- Decision points (ADR 0009 §4): facts of the main flow (`domain.KindDecisionPoint` + `DecisionEvent`, replayed by `Change.DecisionPointsAt(now, policy)`), written only through `Graph.OpenDecision` / `RuleDecision` / `AnswerQuestion` / `RatifyDecision` (`AddItems` refuses the kind); actions reach them through items of kind `decisionPoint` (`pkg/engine/decisions.go`) and the builtin `decision.investigate`. The graph keeps the mechanism (open / rule / answer / ratify, who ruled, the statuses, the gate, an option selected by a decided point); when a ruling settles a point and when only a person may rule it is a policy (ADR 0067): the opener's `Policy` values are stored opaque on the point, `Graph.DecisionPolicy` (a `domain.DecisionPolicy`: `Open` / `Fold` / `Reserve`; unset: a ruling of anyone settles) resolves and interprets them, passed as a parameter to the pure replay; `pkg/decision` is the confidence / rounds / deadline policy (`decider`, `threshold` 0.7, `maxRounds` 3, `maxDuration`), plugged explicitly by `cmd/graph` and `cmd/goap-dev` (`g.DecisionPolicy = decision.Policy{}`; tests that use it do the same), and `pkg/graph` / `pkg/domain` must not import it. CEL sees `policy` (a map) and `humanOnly` on a decision point, not `decider` / `threshold` / `rounds`. Conditions see `options`, `activeOption`, `decisionPoints`, `questions`; the conditions of the `decisions` library (`open_questions`, `no_decision_pending`...) exist only in a methodology that imports it (`imports: [decisions]`, `condition.Library`, ADR 0064; same for the `risks` library, whose threshold is `condition.HighRisk`); a condition it declares under the same name wins, and the engine adds none else. The CEL variables stay in every environment (lifecycle guards read them) but `condition.Activation` computes them lazily.
- Authorization is ABAC (Casbin) via `authz.Authorizer`; the rules are `Policy` nodes and the callers `User` nodes of the `organisation` namespace, read by `pkg/access` (compiled-in defaults `pkg/authz/casbin.go` seed them and apply while the graph has none; administrators are never locked out). There is no IAM service.
- Project (ADR 0039): `organisation@ProjectUnit` mirrors `OrgUnit`'s hierarchy (`project_part_of`; root `PROJ-ROOT`, `access.DefaultProject`, self-linked rather than rootless like `ORG-DEFAULT`), naming the methodologies that apply to it. `organisation@Assignment` is the meeting point of organisation and project (`assigns_org` to an `OrgUnit` — `User` is a subtype of `OrgUnit` so it satisfies this too — `assigns_project` to a `ProjectUnit`), carrying the roles a unit or user locally holds there; `pkg/access.Snapshot.ProjectChain`/`ProjectRoles` resolve them, merged into the subject's roles by `access.Authorizer.Authorize` when `authz.Resource.ProjectID` is set (`pkg/engine` threads `Process.Project` into `stepAllowed`'s check). `domain.Change.ProjectID` names the project a change acts in, named when `CreateChange` stores it (ADR 0091: no change without a project, no default project and no `default` flag on `ProjectUnit`; a sub-change takes its parent's; the edges resolve the caller's active project, an empty claim meaning the root, `graphsvc.Handler.projectOf`, `Engine.resolveChange`, `goap-change/create`, the assistant; a run on an existing change works in that change's project); it changes only through `Graph.MoveChange` (RPC `MoveChange`, `goap-change/move`, `change:move`, web "Move to project…"): a root change, draft or active, with its open sub-changes, in one transaction, when `Graph.ProjectMoveGate` (`graphsvc.ProjectMoveGate`, plugged by `cmd/graph` and `goap-dev`) accepts: `change:move` and access on both projects and the methodology of each change applicable to both;
