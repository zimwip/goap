# GOAP — notes for contributors and agents

- **English is the project's official language.** All code, comments, docs, commit messages, and UI text must be in English.
- Architecture and concepts: `docs/architecture.md`. Keep it in sync with code changes.

## Mental model: who, why, how, what, with what

GOAP manages the whole scope of an enterprise. **Organisations work on the Domain to change it as their needs
require. The need is the intent of a Change; how they perform it is the Methodology; its actions say which tools
they use.** Every design decision starts by asking which of these questions it answers, and lives in that concept.

| Question | Concept | What it is | Where it lives |
|---|---|---|---|
| **WHO** | **Organisation** | Who acts, and the scope of responsibility. A hierarchy of units (`OrgUnit`, `part_of`); the default unit `ORG-DEFAULT` is the root of every unit. A unit holds changes, the adapters of its tools and its users; who may do what (`Policy` nodes, ADR 0020) lives here too; a user holds no role of its own but the `admin` flag, its roles are held on projects (ADR 0043). Mirrored by a hierarchy of **Project** (`ProjectUnit`, `project_part_of`, root `PROJ-ROOT`): what the organisation works on, identifying the methodologies that apply and so the roles they inherit (ADR 0035 §2, ADR 0039). A `Change` belongs to a project (`ProjectID`). | graph, `organisation` namespace |
| **WHY** | **Change** (intent) | The reason to act, and the blackboard of the execution: everything that modifies the graph goes through one. It has an intent, an owner unit, a methodology, and acts on one namespace. Agents and actions work on it. Pure questions about the world state need none. | `domain.Change` |
| **HOW** | **Methodology** | How a change is performed: goals, conditions, agents, actions, triggers. | graph, `methodology` namespace (`MethodologyVersion` + element nodes typed by the `methodology` meta-domain, ADR 0023) |
| ↳ | **Agent** | A broad task scope that needs planning and loops to be achieved (goap / utility / hybrid planner); may call sub-agents. | methodology |
| ↳ | **Action** | The smallest task, not splittable: preconditions, effects, cost. Kinds `llm`, `tool`, `human`, `builtin`, `script`. It states the tools (MCPs) it uses. | methodology |
| **WHAT** | **Domain** | What is being changed: node types, links, lifecycles, algorithms (`alm`, `organisation`, `platform`, ...). One domain per namespace; a type is referenced as `<namespace>@<NodeType>` (ADR 0012, 0013). The versioned graph is its content. | `domains/`, registry database (`domain_version`); each graph holds the published ones in memory (type catalogue) |
| **WITH WHAT** | **MCP, Connector, Adapter** | **MCP**: the generic usage of a tool by an LLM (`platform` namespace). **Connector**: the driver of a real service, a separate service that registers itself. **Adapter**: the code that implements the tools an MCP expects with the operations a connector exposes. It is an `AdapterDef` node of the `platform` namespace (usage `adapter`, template generated from the MCP and the connector), changed through a Change; a unit holds an *instance* with its parameter values (secrets as references), where organisation, MCP and connector converge (`Adapter` node, `organisation` namespace, owned by the unit: the owner of its version, ADR 0054). | graph + connector registry (MCP hub) |

Design rules that follow, to keep the whole consistent:

1. **Keep the concepts independent; couple only at the designated meeting points.** A methodology knows no
   organisation and no connector (it names MCPs; it references the types of domains, `alm@Requirement`). An MCP knows no connector
   and no adapter. A connector knows no MCP and no organisation. A domain knows no methodology. The **Adapter** is
   where organisation, MCP and connector meet; the **Assignment** (`organisation@Assignment`, ADR 0039) is where
   organisation and project meet, carrying the roles a unit or user locally holds on a project; the **Change** is
   where who, why, how and what meet at run time.
2. **Every modification is a Change.** No write to the graph outside one (the direct-write endpoints are for
   seeding and non-controlled nodes only), and every change names its intent (why), its holding unit (who), its
   methodology (how) and its namespace (what).
3. **Responsibility flows down the organisation.** Anything an organisation provides (adapters today, policies and
   quotas tomorrow) is resolved from the unit holding the change, then its ancestors, then `ORG-DEFAULT`: the nearest
   wins. Units share an MCP and a connector with different scopes (same file access, different root directory).
4. **What describes the enterprise is graph data, changed through changes** (organisation, adapters, MCPs,
   methodologies): versioned, reviewable, journaled. The exceptions: the domains, which define the graph itself (the
   registry versions them in its database, each graph holds them in memory, ADR 0023), service configuration and
   runtime registrations (a connector announcing itself and its liveness).
5. **What is available comes from who.** An action is schedulable only where the unit holding the change resolves the
   MCPs it declares (`mcps:`); an agent may declare MCPs for its llm / script actions. ABAC decides what a principal
   may do; adapters decide what the organisation can reach.
6. **Agents plan, actions execute.** An action does one thing; anything that needs a loop, a choice or planning is an
   agent over smaller actions.
7. **Library and instance.** Whatever is reusable across organisations is written once in the domain library (an
   algorithm with declared parameters, ADR 0018) and instantiated where it is used with parameter values: an adapter
   is a definition (`AdapterDef`), and each unit gives it its own scope (same adapter, another root directory).
8. **Adding a capability**: name the question it answers, put it in that concept, and cross concepts only at the
   meeting points above. Adding a real service is a new connector (a service that registers itself), never a change to
   the platform.

## Working notes

- Go module `github.com/zimwip/goap`; core logic in `pkg/` (no infra deps), services in `internal/` + `cmd/`.
- Contracts: `proto/` → `make generate` (buf) → `gen/` (committed, never edit by hand). The protos keep no `reserved` fields: clients and services ship together and the database starts from zero, so a removed field simply goes.
- Tests: `make test`; PostgreSQL-backed tests (graph) run when `GOAP_TEST_PG_DSN` is set (`internal/pgtest`); SQLite variants always run.
- Storage has two SQL dialects: PostgreSQL (`migrations/`) and SQLite for the local mode (`migrations_sqlite/`, `make devlocal`, ADR 0010); schema changes go to both, and `TestSchemasAligned` (`internal/sqlschematest`, in `pkg/graph`, `credsvc`, `mcpsvc`, `modelgw`, `prefssvc`, `registrysvc`) fails on any difference of tables, columns, defaults, keys, constraints or indexes (ADR 0074). A graph query both repositories run is written once in `pkg/graph/sqlbuild.go` (`dialect` methods returning the text and arguments; a new query goes there, with its text per dialect in `sqlbuild_test.go`); what stays in `postgres.go` / `sqlite.go` is the executor, the scanning and the encodings. `make test-pg` runs every test against PostgreSQL (a throw-away `pgvector/pgvector:pg17` container unless `GOAP_TEST_PG_DSN` is set; there is no CI configuration in the repository, so run it before touching `postgres.go` or a `migrations/` file).
- `make lint` must pass (go vet + gofmt).
- `make.ps1` (and its `make.cmd` launcher) is the Windows twin of the `Makefile`: the same targets doing the same things (`devlocal` runs air with the build settings of `.air.toml` given on the command line, `.air.toml` being written for a POSIX shell); change both together.
- Example methodologies use the domain of `domains/` (`alm`) and the built-in `organisation` and `platform` (loaded in tests with `methodology.LoadFile`). `methodologies/examples/` (`impact-analysis`, `test-design`) is exercised by `pkg/methodology`, `pkg/engine` and registry tests and is not seeded at start (the registry seeds the `*.yaml` directly under `methodologies/`); `methodologies/sdlc.yaml` (ALM domain, demo data of `internal/devseed`) by `pkg/engine/sdlc_test.go`.
- One platform bootstrap (ADR 0071): every composition (`goap-dev`, `cmd/graph`) seeds through `graphsvc.Boot(ctx, g, Options)` — `Graph.Bootstrap`, `SeedAccess`, `SeedBuiltins`, `SeedModels`, then `Options.Dev` — never by calling the seeds itself (`TestCompositionsUseBoot`). Contract: the caller sets the graph hooks and loads the type catalogue first (`Options.RequireHooks` panics without the access hooks; without `SubChangeValidator` / `Lifecycles` (the guardian of the changes), i.e. no registry in process, Boot logs one warning), the registry seeds the methodologies after. Development and demo data is separate (`internal/devseed`: `Demo`, `DocumentRepository`, `LocalFS` for `GOAP_DEV_FS_ROOT`): `goap-dev` passes it as `Options.Dev`, `cmd/graph` only with `GOAP_GRAPH_SEED=demo`; `SeedDefaults` no longer exists. Platform services take their identity from `authz.System(name, roles...)`.
- Versioning rule of the graph: outgoing links belong to the source node version (see `pkg/graph/apply.go`).
- Structures, bootstrap, guard (ADR 0054): a domain tags the node type building the organisation and the one building the projects (`structure: {kind, parent, root, selfParent, bootstrap}` on a node type: `bootstrap` gives the root's initial properties; one per kind across the domains, the built-in organisation domain tags `OrgUnit` / `ProjectUnit`; `TypeCatalog.Structure` / `IsA`, `Graph.Structure`; untyped graph: the catalogue of the built-in domains, `typecat.Builtin()`; ADR 0069: `pkg/graph` and `pkg/domain` name no structure, no root key, `pkg/layering` `TestCoreNamesNoStructure`; the constants of the built-in organisation are `access.DefaultOrg` / `DefaultProject` / `NodeTypeOrgUnit`..., for seeds and tests only). `Graph.Bootstrap` creates the roots the structures declare (`ORG-DEFAULT` and `PROJ-ROOT`) in one transaction and one applied change (services run it at start before any seed; `CreateChange` runs it too). `graph.New` wraps every repository transaction in the guard (`pkg/graph/guard.go`): every node version / link / branch membership (`JoinBranch` takes a change) / node origin names an existing change, every version has an owner unit (`Node.Owner`, stamped from the previous version, else the change's unit; moved only by `NodeUpdate.Owner` / `NodeEdit.Owner`) and every node a project (`Node.Project`, the change's at its first version, never changes), every baseline the result of a change (ADR 0056: the state before a namespace's first change is the empty baseline id, `""`, which nothing stores; `Baseline("")` / `BranchHead` read it), every change a unit and a project (`scopeChange`: the parent's, else the root unit for the unit; the project is never defaulted, a root change naming none is refused with `ErrInvalid`, ADR 0091), checked at the end of the transaction like deferred foreign keys; never bypass it (fixtures write through a change too, `seedNode`). The schema repeats it (`NOT NULL` foreign keys, deferred for the bootstrap; the schema started from zero, `0001_schema.sql`). There is no `organisation@owner` link: ownership is the version's owner (`SplitByOwner`, the adapters of a unit). The services reading the organisation (`pkg/access`, `internal/mcpsvc`) never name its types: they ask the graph for its structures (`Graph.Structures` / RPC `GetStructures`, `domain.Structures`: a list of structures with the types of each, `Organisation()` / `Project()`, a `User` being a unit; both structures live in one namespace, a platform constraint checked by `typecat`) and build their snapshots from them; the walk up a hierarchy is one resolver, `domain.Hierarchy` (`Structures.Hierarchy(kind, nodes, links)`, `Chain(key)`: self first, root last, cycle-safe), used by `access.Snapshot`, `mcpsvc.Snapshot` and the `goap-admin` listings (ADR 0068).
- Change lifecycle and gates (ADR 0058): a change may follow a domain lifecycle named by `Methodology.Lifecycle` (`Change.Lifecycle` / `State`, orthogonal to `ChangeStatus`; resolved through `graph.ChangeLifecycles`, implemented by `registrysvc.Service`, wired in `goap-dev`). `Graph.TransitionChange` checks the transition, `Graph.ChangeAuthorizer` (`change:transition`) and the CEL guard in the condition environment (`condition.CheckGuard`: `change`, `decisionPoints`, `world`); a gate is a guard requiring a decided decision point (`change.decision`, consumed by the move) and the `done` conditions of the steps of the state being left, no checklist of its own. A step is tied to a state by `pre: {"state:<name>": true}` (generated condition). The move is a `KindTransition` fact (written only by `TransitionChange`); leaving a state freezes the impacts whose draft was started in it (the checkout and the edits refuse), going back sets later ones to `proposed`; the merge needs a final state (asked by `checkMerge`, ADR 0102), the commit does not. Keep the platform generic: states and gates are use-case level (domains, methodologies). Web: the change tab lists the transitions out of the state (`ChangeTransitions.svelte`, `web/src/lib/changeTransition.ts`, `graph.transitionChange`) and the assistant has `transition_change` (write, no second dialog). Not yet: engine builtin, `sdlc` lifecycle.
- Baselines and tags (ADR 0056): a baseline is the state a change leaves (`Baseline.ChangeID` mandatory), the first change of a namespace starts from the empty state (`BaselineID ""`, `change.baseline_id` nullable); a name is a `domain.Tag` on the change that left the state (`Graph.TagChange`, not unique: several changes may carry one name); there is no `CreateBaseline`. A change is applied in two steps: `CommitChange` validates it, writes the versions from its drafts (ADR 0079) and records its state on its own branch (baseline `Kind` `commit`, one `landed` event per impact; the change stays `active`, ADR 0102), `IntegrateChange` integrates it into the branch it forked from (`fast-forward`: joins; `merge`: a merge change with its own `landed` events; status `applied`; conflicts leave it `committed`); `Apply` is both. A root change is rebased onto the head of the branch it forked from before it lands (ADR 0101, at its merge since ADR 0102: `RebaseChange`, conflicts stop with `ErrConflict`, a clean rebase keeps the reviews), so landing is a fast-forward and the three-way merge only a race; baselines record `RebasedFrom` and their `Kind`. One commit and merge path (ADR 0102, `pkg/graph/apply.go`, `rebase_committed.go`, `mergecheck.go`; no exception, whoever calls): `CommitChange` (a root change or a sub-change, ADR 0103) writes every accepted modification on the change's branch and reverts the nodes withdrawn since their commit (baseline kind `revert`), never asks the methodology nor rebases, leaves the change `active` (`ResultBaselineID` = its last commit, `hasCommits`), refuses `ErrNothingToCommit` (an `ErrInvalid`, carried over RPC by `rpcerr`'s reason header); `IntegrateChange` / RPC `MergeChange` (`merge`, root or sub) needs everything settled (`unsettled`: committed, none rejected or candidate, no open flow / decision point / sub-change, no pending revert), rebases (a root change's committed branch: `rebaseCommittedTx`, a `rebase` baseline with `MergedFrom` the new fork, both-sides nodes as drafts with `Draft.MergedWith` = the second parent; a clean rebase commits its merges, conflicts stop it; a sub-change onto its parent), asks the guardian of the change (`checkMerge`, `mergecheck.go`: final state of its lifecycle, then `ChangeLifecycles.Merge` — the registry's activity goal, `decided` replaces the next — else the landable states), then fast-forwards; a root change that committed nothing has nothing to rebase (the ADR 0101 draft rebase is gone); `committed` only means a three-way merge waiting for its resolutions. `Apply` = commit what is pending + merge; `Graph.CommitState` / RPC `GetCommitState` drives the web's Commit / Merge buttons (`changeCommit.ts`). Only a modification is accepted and committed (`domain.DraftChanged`, `Graph.draftModifies`, `checkModifies`, `ImpactValidation.Modified`): a candidate or an unchanged draft is refused at accept; a source of a merge / split (`via`) is decided by its parent's impact (`checkOrigins`); `Graph.Commit` withdraws its edits that restate the graph (`ErrNothingToCommit` when none is left, change purged; seeds and the registry store take it as "already there"). Web: `baselineHistory.ts` lanes of open forked branches (`LaneEntry.pending`). A change is its branch (given at commit when it has none). A baseline's state is derived from what its change did (`landed` events, or the versions joined for a fast-forward), so only every `MaterializeEvery`-th baseline of a chain stores its entries (`Baseline.Gap` 0, `GOAP_MATERIALIZE_EVERY`, 1: all) and the others are a header, replayed and cached by the guard (`pkg/graph/state.go`; reads through the guard always hold the nodes, `Graph.Materialize` stores one). Run the suites with `GOAP_MATERIALIZE_EVERY=1`, `3` and `100000` after touching baselines: `checkStates` replays every baseline. `Apply`'s `baselineName` tags the change when it differs from its title. The check of the change impacts at commit is `walkChangeImpacts` (properties, `walkTransitions`; ADR 0072); the guards and actions of a lifecycle move run when it is taken (`ImpactNodeTransition`, `checkTransition` / `runActions`), the refusal of nodes left in a state that cannot land (ADR 0078) is the merge's (`checkMerge`); `walkTransitions` follows the in-place moves recorded in the log of the change that wrote a version (ADR 0077).
- Drafts and versions at landing (ADR 0079; ADR 0076 checkout, ADR 0077 naming, merge and split, ADR 0078 landable states): a node has **no version during a change**. Every node write names a change (no `CreateObject`, no change-less write); `Graph.ImpactNodeCreate` / `ImpactNodeCheckout` give the node a **draft** per change impact and flow (derived from the change log, not stored: `domain.FoldDrafts`, read through `Graph.drafts`, a per-change cache validated by the log's last seq, `pkg/graph/draftcache.go`; `domain.Draft`: node id allocated at `created`, key, type, state, owner, properties, origins, `Base` = the version checked out from, outgoing links to an exact version or to a draft reference), once per change and flow (`graph.IsWorking`; a second checkout is `ErrConflict`, a child flow copies the parent flow's draft, `forkDraft`), and the impact's post is the **draft reference** `NodeRef{ID, Version: 0}` (`NodeRef.IsDraft`, `ChangeImpact.Drafted`; a draft reference is read through the change: `Graph.ChangeNodeView` / `ChangeNode`, `GetNode` with `change_id`, the blackboard and `ChangeView` hydrate it under that key, `draftReader` in `pkg/graph/draft.go`). `ImpactNodeUpdate` (props, owner) and `ImpactLinkCreate` / `ImpactLinkUpdate` / `ImpactLinkDelete` edit the draft (an `updated` event with the patch); the drafts are written only through `Graph.emit` (ADR 0029), by `domain.ApplyDraftEvent` over the events (`created` / `checkedOut` carry the initial `Draft`, `updated` / `transitioned` patches, `cancelled` / `withdrawn` / `landed` drop it; an adoption installs the flow's drafts on the main flow with `transitioned` events carrying a `Draft`), and `domain.FoldDrafts` rebuilds them from the log (`checkImpactLogs` replays every change on both repositories). **Reviews are always explicit**: an edit, a transition or a link edit never reviews (the producer paths `Graph.Commit` / `CommitEdits`, seeds, `EnsureUser` and `graphtest` review explicitly, by the same rules); only a modification is accepted (ADR 0102); an accepted review is the gate of what a version must satisfy, run on the draft (`checkAccepted` → `checkDraft`: attributes, validators, required links, link attributes, origins) and writes nothing; an edit of the content (properties, owner, links) or a cancel sends a decided review, accepted or rejected, back to `proposed` (`editedAgain`: a rejected impact is reworked so, or withdrawn); a checkout and a lifecycle move leave the review. `ImpactNodeTransition` sets the state of the draft (`transitioned` event, patch `{"state": {from, to}}` and the properties its actions set; a node with no draft is checked out first, keeping the review; the CEL guard sees `node`, `change`, `impact` and `draft`, `guard.Guard.Check`); `ImpactNodeCancel` drops a draft (a creation cancelled removes its impact; one committed falls back to its committed version), `WithdrawImpact` takes an impact out of the change at any time (with the impacts `via` it; one committed is reverted by the next commit); a rejected impact keeps its draft (`ReopenImpacts` reopens rejected ones too). **Landing** (`CommitChange`, so `Apply`; `prepareChangeImpacts`: the accepted modifications only) validates every draft again and **writes the versions** from the drafts in the commit transaction (`writeVersion`: the next number, `Parents` = the version checked out from, owner, origins, comment = last review comment, then the links, a draft reference or the version a draft was checked out from resolved to the version this landing writes for the node), on the change's own branch: no `node_version` row existed before, a version is immutable once written (the guard accepts links only for a version written in the transaction; `Tx` has no edit, freeze or drop of a version), the `landed` events then name the versions (the impact's post becomes the landed ref), node index events are published for them. A draft equal to its base is not a modification: it is neither accepted nor committed (ADR 0102). A node whose branch head moved since the draft was checked out is a conflict at landing (no longer a sub-change's doing: ADR 0081). Branches, `IntegrateChange` (fast-forward / 3-way merge) and baselines are unchanged: the commit step is where versions appear. The lifecycle phases of ADR 0058 follow the events that start a draft (`ImpactEvent.StartsDraft`), `walkTransitions` replays the recorded moves of a draft. Flows keep no branch: a flow's drafts are its own rows, `seenDrafts` / `DraftSeenBy` give what a flow sees (the innermost draft of its chain, the stale runs of ADR 0025 left out); adopting a flow (`adoptNodes`) installs its drafts on the main flow (a conflict when the main flow's moved on since) and resets the main drafts the stale runs wrote. A node is never deleted: removing a child is a modification of its parent; a node no parent holds is retired by its lifecycle (`config`: `active` / `retired`, on the MCPs, adapter definitions and model entries of `platform`, the adapters, policies and assignments of `organisation`; `access.InForce` leaves retired nodes out of the access and hub snapshots; `CommitEdits`' `state` retires, and restores a retired node in the same change as its edits; `Graph.Commit` moves a node with a draft to its state, then accepts it: a created user is one version). Edits are allowed in any state; a lifecycle state may be flagged `notLandable` (ADR 0078, `Lifecycle.Landable`: default landable) and a change lands only when each node ends in a landable state (`Lifecycle.Issues`: a not landable state must reach a landable one, a final state is landable). `graphtest` lands fixtures through these operations (`Import`, `Edit`, `Project`, `Unit`).
- Merge and split (ADR 0077, "Merge and split"): a node is never retired by one; merging A and B into C is a modification of their parents (nodes holding a `compose: true` link to them): the parent's draft loses the links to the sources and gains one to the new node (`Graph.ImpactNodeMerge` / `ImpactNodeSplit`, `pkg/graph/restructure.go`, one transaction over `resolve`; `TypeCatalog.Composes`), the sources' impacts carry `via` = the parent's impact, other links to a merged source follow it and ones to a split source are returned as suspect. The successor's draft records its origins, written to `Node.Origins` of its first version at landing (a `node_version.origins` column, `Graph.DerivedNodes` / `sqlDerivedNodes`, `patch.origins` of the `created` event, PROV `wasDerivedFrom`); `checkOrigins` holds its review and landing until the impacts of its origins are accepted. `MergeInput.Gate` carries the `adminOnly` gate over the parents it finds. Same names in the RPCs, `engine.GraphPort`, the DSL (`ctx.impactNodeMerge` / `impactNodeSplit`), the `goap-change` tools `merge` / `split` and `web/src/lib/api/graph.ts`.
- Sub-changes on their own branch (ADR 0103, superseding ADR 0081 / 0082 and ADR 0016 §3-4): a sub-change (`Change.ParentID`) is forked from the head of its parent change's branch (`prepareSubChange`; the parent gets one), recursively, and is a change like any other: it commits on its branch (`CommitChange`) and merges into its parent's (`IntegrateChange` → `merge`: `unsettled`, `checkParentDrafts` (a parent's uncommitted modifying draft of a node the sub-change changed holds the merge), rebase onto the parent's head (`rebaseCommittedTx`), `checkMerge` (its own guardian), `fastForward`, then `recordInParent`: per landed node an impact of the parent (else a new one, `producedBy: graph.merge`, `derivedFrom` the sub's impact) gets an accepted review ("merged from sub-change …") and a `landed` event at the parent's head; the parent then has committed work to merge). It sees what its parent committed, never its drafts (`ChangeNodeViewByKey` reads its own branch). No inherited drafts (`Draft.Inherited`, `inheritDraft`, `integrateSub` and the `integrated` event are gone; the database starts from zero, so no legacy event or item kind is read). Web: same Commit / Merge buttons ("Merge into parent") on the change overview, `SubChangeSync.svelte` from `GetRebaseState` (`web/src/lib/rebase.ts`), `SubChangeHistory.svelte` (`web/src/lib/subChangeHistory.ts`: a sub-change's lane starts where its parent stood, its `rebased` events, the "merged" edge from its landing of a version to the parent's). Tests: `pkg/graph/subchange_test.go`, `subchange_nested_test.go`.
- Methodologies integrating methodologies (ADR 0106): a methodology declares `integrates: [{methodologies, exclusive, attach}]` and `guardian: {merge, transitions}` (`pkg/methodology/integrate.go`, `IntegratesChangesOf`, `MergeGuard`: `integrator.attached` first when exclusive, `TransitionGuard`; compile check `checkIntegration`; attributes of `methodology@MethodologyVersion`, proto `Methodology.integrates` / `guardian`); levels are derived, never declared. The guardian chain is saved on the change (`Change.Guardians`, `domain.GuardianRef{Methodology, Version}`, column `guardians` in both dialects, proto `Change.guardians`): a sub-change takes its parent's plus its own methodology (`chainUnder`), a root change `ChangeLifecycles.Guardians(methodology, project)` (registry: `integrates` walked upwards over `Service.Applicable`, wired by `goap-dev` from `access.Snapshot.ApplicableMethodologies`; `cmd/registry` has none). `checkMerge` (own guardian first, `ownGuardianMerge`) and `TransitionChange` then call `checkGuardians` (`ChangeLifecycles.CheckGuardians(bb, transition, ancestors)`, innermost first, CEL `integrator` `{attached, id, methodology, state, status}` of the nearest ancestor of that methodology, `guard.NoIntegrator`; refusal `ErrConflict`). `Graph.AttachChange` / `DetachChange` (`pkg/graph/attach.go`, operations `change.attach` / `change.detach` asked on the parent, RPCs, `engine.GraphPort`): an open root change becomes a sub-change of a change whose methodology integrates its own (`ChangeLifecycles.Integrates`), forked again from the parent's branch with what it committed rebased (`reparent`; `PutBranch` updates `parent`), its chain journaled in a `change.updated` entry. `on:` takes `from: self | integrated | integrator` (`Subscription.Origin`); `Engine.relay` (`pkg/engine/companion.go`) carries a change's events to its parent and open sub-changes (`vars.event.relation`). Events `change.transitioned`, `change.committed`, `change.attached`, `change.detached`. Attach / detach also from `goap-change` (`attach`, `detach`), the change tab (*Attach to change…*, *Detach*, a *Guardians* row; `web/src/lib/changeAttach.ts`) and the assistant at level change (`attach_change` / `detach_change` proposals, `internal/assistantsvc/relate.go`, confirmed by `ConfirmAction`). The registry refuses an integration cycle at validation (`integrationIssues`) and checks the composition (`compositionIssues` → `methodology.CompositionIssues`, `pkg/methodology/composition.go`: events never emitted by their source, unknown states / transitions / steps / conditions in filters and guards, guards never holding alone or along the chain; warnings with `Issue.Hint`, proto `Issue.hint`, shown by the Problems console, `DraftHeader` and `IssueHints.svelte`; the web form keeps `lifecycle`, `integrates`, `guardian`, `on[].from`, *Composition* card of the methodology overview); `MoveChange` recomputes the chain; `cmd/registry` wires `Applicable` too, `cmd/graph` wires no `ChangeLifecycles` (no chain there). First integrator: `methodologies/release-based.yaml` (lifecycle `delivery` of `alm`, integrates `sdlc` exclusively; in force only on projects that list it).
- Dependencies between changes (ADR 0108): `Change.DependsOn` (column `depends_on` in both dialects, proto `Change.depends_on`), set only by `Graph.SetChangeDependencies` (`//goap:operation change.depend doer`; open change, no itself / ancestor / sub-change / cycle / abandoned change; a `change.updated` entry `dependsOn {from, to}`; `AttachChange` refuses a parent related by a dependency). - Decision points (ADR 0009 §4): facts of the main flow (`domain.KindDecisionPoint` + `DecisionEvent`, replayed by `Change.DecisionPointsAt(now, policy)`), written only through `Graph.OpenDecision` / `RuleDecision` / `AnswerQuestion` / `RatifyDecision` (`AddItems` refuses the kind); actions reach them through items of kind `decisionPoint` (`pkg/engine/decisions.go`) and the builtin `decision.investigate`. - User bootstrap, mandatory parenting, local auth (ADR 0040): `EnsureUser` resolves `ORG-DEFAULT` *before* creating anything (the graph is bootstrapped before serving, ADR 0054; creating the `User` first would leave a permanently broken one — no `member_of`, no admin — if the root were missing, and defeat the first-admin bootstrap for everyone after), then links the new user `member_of` it and, when it is the first `User` node the namespace has ever held, grants it `admin` through a platform Assignment created in the same commit (ADR 0046, 0047; `access.PlatformAssignmentKey`, linked by `ToKey` to the `User` node being created in the same edit), checked with `g.NodesOfType` against *live* state (`tx.LatestNodes`), not a baseline snapshot (a benign race can only grant admin to more than one subject, never to none). `pkg/graph.Commit` refuses to create an `OrgUnit`/`ProjectUnit` without exactly one `part_of`/`project_part_of` link (except `ORG-DEFAULT`/`PROJ-ROOT` themselves) and a node whose type declares `requires: [{link, count}]` without those links (`organisation@User`: one `member_of`; `def.NodeType.Requires`, `domain.RequiredLink`, `TypeCatalog.Requires`, untyped graph: the built-in catalogue, ADR 0065) (`checkRequiredParent`, checked against the edit's own declared links before anything is written); `checkRequiredLinks` (`pkg/graph/subchange.go`) additionally re-reads a *modified* node's actual live links right after the write, since a client (e.g. the "move" action, `graphEdit.moveNodeItem`, "Move to…" on the Organisation/User tabs) can work off a `headGraph` baseline snapshot that predates an import-written link and so not know one already exists — refusing a resulting second link rather than silently leaving two. - Front location and session (ADR 0052): the active tab is the URL path and query (`web/src/lib/shell/router.ts`, `startRouting` in `tabs.svelte.ts`); tabs, project, explorer state are not in `localStorage`; the project is the token claim; a sign-in/out (token appears/disappears, any tab) clears per-user storage and reloads on home (`stores/auth.svelte.ts`, `restartOnSessionChange`); a 401 ends the session in every auth mode. - Server-side sessions (ADR 0045): register/login open a session in `internal/credsvc` (`auth_session`, both dialects; `Service.StartSession` / `SessionActive` / `EndSession` / `EndSessions`, Connect `credentials.v1`; `SetPassword` ends the subject's sessions); tokens carry its id (`sid`, kept by refresh and project switch). - Service identity and trust (security phase P0): every graph RPC is identified (`Handler.Identify`, first interceptor; an anonymous request is refused, the transition authorizers no longer trust an anonymous context); platform services act under a named `system:` subject (`authz.Principal.System`; `graphsvc.SystemPrincipal` for seeds and sign-in bookkeeping, `graphsvc.ClientPrincipal` for a `graphsvc.Client` call with no principal) and are never users (`EnsureUser` skips them, so they cannot take the first-admin grant). One question, `Graph.AdminOnlyType` (ADR 0068: `adminOnly: true` on a node type of a domain, inherited by subtypes; the built-in domains flag OrgUnit, User, Policy, ProjectUnit, Assignment, Adapter, AdapterDef, CriticalityPolicy, LlmBehavior; `TypeCatalog.AdminOnly`, untyped graph: the built-in catalogue), gates those nodes in the graph handler and in `goap-change` (`Change.gate`, through `engine.GraphPort.AdminOnlyType`, RPC `IsAdminOnlyType` for `graphsvc.Client`); a domain's new access-controlling type is one flag. - Project-scoped roles (ADR 0043; administration itself became a platform role in ADR 0047, superseding this ADR's "admin is a flag" decision — see below): every role a user holds is granted by an `Assignment`, a project-scoped one holding a methodology's (`methodology@Role`), needed by a project through its applicable methodologies (inherited by sub-projects); `access.Authorizer.Authorize` merges the roles of the subject's chain (`Snapshot.SubjectChain`: `USR:<subject>`, its unit, ancestors) on the resource's project chain (root project when none) into `r.sub.Roles`, for every request. Default policies (`authz.DefaultPolicies`, seeded once by `graphsvc.SeedAccess`): admin everything, `onProject(r.sub)` for process/object/node/tool/change-apply, `mayRun(r.sub, r.obj)` for `action:run`, `agent:run`, `model:use` (`r.obj.Roles`); methodologies, domains, triggers, organisation, policies, adapters are admin-only. Agents and actions declare `roles: [...]` (checked against the methodology's roles; trigger roles are not); the engine checks them (`Engine.runRoles` / `mayRun` / `checkAgentRoles`, which read the methodology and ask the `engine.Scope` port with plain data; an action the initiator may not run waits for an `action:run` approval, a human one for a submitter holding the role) and acts as `ProcessRef.Actor` (initiator on the process's project). Resources thread `ProjectID` (enginesvc, graphsvc `ImpactNodeCreate`, transitions, mcpsvc tool calls, modelgw). Web: `web/src/lib/projectRoles.ts` (roles a project needs, who holds them), Project tab, Assignments pane role picker; the types, keys and roles it names come from the session (ADR 0070).
- Platform roles, administration migrated (ADR 0046, 0047): a fixed, built-in catalog of the platform namespace (`platform@Role`, `access.BuiltinRoles`: "admin", "reader"; kept in sync with the code by `SeedBuiltins` the way the built-in MCPs are, ADR 0028) granted by an `organisation@Assignment` naming no project (`assigns_org` only, key `access.PlatformAssignmentKey`); `access.RoleAdmin`/`RoleReader` name them for the ABAC rules, `access.PlatformRoles` lists the grantable names. `Snapshot.PlatformRoles` resolves it over the org chain; `Snapshot.Enrich` merges it in unconditionally (resource-independent, so `Authorizer.Floor()`, which calls only `Enrich`, sees a platform-granted admin too — no stored policy can lock one out, ADR 0020/0043), alongside the project-scoped roles `Authorize` adds for the request's resource. - Attributes (ADR 0055): a node type or link type defines its properties as `Attribute`s (code, label, type, widget, enum, default, section, order, tooltip, `asName`, and the `property_validator` instances plugged on it; a bare name is shorthand), resolved by the type catalogue (ancestors first, overridable by name); a domain declares `enums`; node types plug `node_validator` instances. The graph checks the type / enum membership of values on commit; attributes are **strict**: a property that is not an attribute of the node's type (own or inherited) is refused with `ErrInvalid` by `typeIndex.checkAttributes` (so at create, update, checkout, transition, accept and landing; `TypeCatalog.AttributeNames(typ) (names, open)`), unless the type is flagged `additionalProperties: true` on the node type (`def.NodeType.AdditionalProperties`, inherited, registry proto `NodeType.additional_properties` / `TypeInfo.additional_properties`, a checkbox of `NodeTypeMeta.svelte`, `TypeCatalog.open` / `LifecycleRow.open` in the web); the untyped graph and a type unknown to the catalogue stay permissive. - Domain model (ADR 0060): the definition of a domain (`Domain`, `Schema`, node / link types, attributes, enums, lifecycles, algorithms, the built-in domains, `Issue` / `Issues`) lives in `pkg/domain/def`, which `pkg/methodology`, `pkg/typecat`, `pkg/graph` and the services import; `pkg/methodology` keeps only what is specific to a methodology (actions, agents, processes, compilation, `LoadFile`) and a domain knows no methodology.
- Node types (ADR 0012, 0013): a node's type is composite, `<namespace>@<NodeType>` (one domain per namespace: `alm`, ...; shipped with the code and frozen, `domains/builtin/`: the meta-domain `methodology`, `organisation` and `platform`; a new namespace is a new domain); every type or link type reference is qualified. The registry is the reference of the types (published domains); the graph and the engine keep an in-memory type catalogue loaded from it at startup and synced by its events (lifecycle, validators, search, editor, `extends`), and the graph refuses an unknown type. Nothing is projected onto the graph.
- Methodologies are graph nodes (ADR 0023): a version node (`MV:`) and one node per element typed by the meta-domain (`methodology@Agent`, ...), kept by `registrysvc.GraphStore`. Domains are the definition of a graph, not graph data: the registry keeps them in its database (`registrysvc.SQLDomainStore`, `internal/registrysvc/migrations*/`). YAML is import/export only.
- Processes (ADR 0034): a methodology's `processes` are trees of steps (sub-steps, `action`, alternative `actions`, `agent`, nested `process`, or manual) sequenced by their conditions only (never by position), with `references` to their reference documents, compiled by `pkg/methodology/process.go` into an agent + goal per process and one action per step (named by its path); agent, nested-process and method steps run through the builtin `process.step` (`pkg/engine/steps.go`) as sub-agents on the same change. Methods (ADR 0035, reshaped by ADR 0050, `pkg/methodology/method.go`) are references, never actors, and name no agent: a method owns `actions` (a pool its steps inherit) and/or `steps`, with `done`, `planner`, `model`, `mcps`; compiling it generates an agent of its name (`Agent.Role` = its responsible role) run as a fresh sub-agent per step; a step naming a capability (`method:`) runs the applicable method (priority, then the most specific `when`, `Method.Specificity`), once per element of its `foreach` CEL list (`groupBy`: per group) in parallel streams with `vars.item` bound (`pkg/engine/foreach.go`, `Lane` in the progress). `Engine.Progress` (`pkg/engine/progress.go`) is the read model of a run's process. Roles (ADR 0035 §2): a methodology declares `roles`, steps and methods assign them RACI style; users hold them on projects through Assignments (ADR 0043; a token may still carry one unscoped or per unit, `role@UNIT`, `authz.Principal.HasRoleIn` + `Resource.OrgChain`); `step:perform` / `step:approve` are checked by the engine.
- Compilation issues guide the user (`pkg/methodology/issues.go`): one pipeline (`pkg/methodology/compile.go`, ADR 0072: `CompileWith(CompileOptions{Lenient, Stored})`, a phase per `compileState` method; a compiler panic is a bug, never caught): `Compile` refuses a methodology with issues, `CompileLenient` builds what stands and returns the issues with it (`PreviewPlan` too, with the issues alongside the plan), `ValidateStored` adds the namespace rule; the registry caches compiled methodologies (`registrysvc.compileCache`: name, version, content hash, domains in force), each `Issue.Activity` tied to the process, method or step it is about (`Methodology.ActivityOf`); `GetProcessGraph` / `CheckLevels` use it, so the flow of a draft with broken rules is drawn as far as it stands (`DraftFlow` → `ProcessFlowView` marks the steps, lists the rules in its panel) and the Issues console and the editors' fields keep pointing at the definition path. `Issue.Severity` (ADR 0097): `error` (default) refuses, `warning` never does; refusals test `Issues.HasErrors()`, never `len(issues)`; `CompileWith` appends `Compiled.Hints()` as `goal` warnings when there is no error; the web splits them with `web/src/lib/issues.ts`.
- A condition is never both an input and an output of an action or a step, whatever the values (ADR 0051, `overlap` in `pkg/methodology`): no `pre: {x: false}` guard next to `effects: {x: true}`; the planners never repeat an action whose effects already hold. The compiler refuses it, tied to the step (`Issue.Activity`), and the flow draws it red (`GapNoop`).
- Agents (goap/utility/hybrid planners) and script actions (JS via goja, Go via yaegi) use the DSL in `pkg/dsl` (docs/dsl.md); scripts run in sandboxes (`internal/sandbox`, `GOAP_SANDBOX`).

Web: `ChangeAsks.svelte` at the top of the change overview (*Waiting for you*, answered in place through `PendingTask.svelte`, the pending-task switch shared with `RunTab.svelte`; *Waiting for others*; the impacts awaiting review), `web/src/lib/changeAsks.ts`. Not yet: notifications to role holders, a cross-change inbox, the shared thread of the change, agents asking a role (the ADR's next steps).
- Execution journal (ADR 0011): the engine records ticks / actions / approvals on the change (`journal.Record`, `pkg/journal`, ADR 0066: the graph holds a generic typed log, `Graph.AppendLog` / `ChangeLog`, refusing the `fact` / `impact` streams it writes itself, and `pkg/graph` / `pkg/domain` must not import `pkg/journal`, `pkg/layering`; `journal.Append` / `Read` work over any `journal.Log`, `engine.GraphPort` has `AppendLog` / `ChangeLog`); items carry `execution`. The observer (`methodologies/methodology-improvement.yaml`, `pkg/observe`) turns runs into change impacts on the definition nodes of a methodology draft.
- Builtin actions (ADR 0062): their names are constants of the leaf package `pkg/builtins` (with `All()` / `Known`); `Methodology.Builtins` (`WithBuiltins`, a `methodology.BuiltinSet`) makes the compiler refuse an unknown `builtin:` (nil: unchecked), and `registrysvc` always sets `builtins.Known{}`. `engine.BuiltinExecutor` is the engine's table (`Register` panics on a duplicate, `HasBuiltin`); `DefaultBuiltins()` holds the five generic ones (`derogation.expire` among them). The self-observation builtins live in `pkg/selfimprove` (`Register(b, e, Config)`, called by `cmd/engine` and `cmd/goap-dev`): `pkg/engine` imports no `pkg/observe` (`pkg/layering`). A new builtin: a constant in `pkg/builtins` and a `Register` call.
- `web/src/lib/help/dsl.md` is a copy of `docs/dsl.md` (the web dev container only mounts `web/`); `make lint` checks they are identical.
- Svelte 5 rune state modules (`*.svelte.ts`) must not share a base name with a component (`*.svelte`) in the same directory (e.g. `searchOverlay.svelte.ts` next to `SearchOverlay.svelte`): on case-insensitive filesystems (Windows, default macOS), an extensionless import of the state module (`from './foo.svelte'`) resolves to the component file instead, since Vite tries an exact match before extending to `.svelte.ts`. This builds fine on case-sensitive Linux CI and only breaks locally on Windows/macOS. Either name the pair distinctly or always import the state module with its full extension (`from './foo.svelte.ts'`).
- One event stream and presence (ADR 0053): `internal/eventsvc` (`Hub` is a `Publisher`/`EventSink` fed in process by `goap-dev`, from NATS by `cmd/events`; `Watch` resumes by `(epoch, seq)` or says `resync`; `Heartbeat`/`Leave` are the presence, in memory with a TTL). The graph publishes `change.updated` (`goap.changed.<id>`) for every change header / impact / log write, so a new write path needs no extra event. Web: never refetch after a write; `web/src/lib/flux/` (`events.svelte.ts` the one stream, `reducers.svelte.ts` events → `signals.svelte.ts` stamps; a view that loads depends on `stamp(keyOf.…)` in its `$effect`); every `rpc` carries `X-Goap-Command`.
