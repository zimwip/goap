# GOAP — notes for contributors and agents

- **English is the project's official language.** All code, comments, docs, commit messages, and UI text must be in English.
- Architecture and concepts: `docs/architecture.md`. Keep it in sync with code changes.
- Architecture overview: `docs/architecture-overview.html` (open it in a browser) draws the modules (logical), the services and their flows (physical: one container per binary of `platform/cmd`, with its port) and one step of a change end to end. Update it in the same change whenever you add, remove or rename a module, a binary, a compose service or a port, or change who calls whom (a new client, a new event on NATS, a route of the gateway): the boxes, the wires, the *Deployment units* table and the numbered run. `platform/layering` `TestArchitectureOverview` fails while a module (`data-module`), a binary (`data-binary`) or a compose service (`data-service`) is missing from it; the flows it cannot check, so read the page again when you touch them.

## Mental model: who, why, how, what, with what

GOAP manages the whole scope of an enterprise. **Organisations work on the Domain to change it as their needs
require. The need is the intent of a Change; how they perform it is the Methodology; its actions say which tools
they use.** Every design decision starts by asking which of these questions it answers, and lives in that concept.

| Question | Concept | What it is | Where it lives |
|---|---|---|---|
| **WHO** | **Organisation** | Who acts, and the scope of responsibility. A hierarchy of units (`OrgUnit`, `part_of`); the default unit `ORG-DEFAULT` is the root of every unit. A unit holds changes, the adapters of its tools and its users; who may do what (`Policy` nodes, ADR 0020) lives here too; a user holds no role of its own but the `admin` flag, its roles are held on projects (ADR 0043). Mirrored by a hierarchy of **Project** (`ProjectUnit`, `project_part_of`, root `PROJ-ROOT`): what the organisation works on, identifying the methodologies that apply and so the roles they inherit (ADR 0035 §2, ADR 0039). A `Change` belongs to a project (`ProjectID`). | graph, `organisation` namespace |
| **WHY** | **Change** (intent) | The reason to act, and the blackboard of the execution: everything that modifies the graph goes through one. It has an intent, an owner unit, a methodology, and acts on one namespace. Agents and actions work on it. Pure questions about the world state need none. | `domain.Change` |
| **HOW** | **Methodology** | How a change is performed: goals, conditions, agents, actions, triggers. | graph, `methodology` namespace (`MethodologyVersion` + element nodes typed by the `methodology` meta-domain, ADR 0023) |
| ↳ | **Agent** | A broad task scope that needs planning and loops to be achieved (goap / utility / hybrid planner); may call sub-agents. | methodology |
| ↳ | **Action** | The smallest task, not splittable: preconditions, effects, cost. Kinds `llm`, `tool`, `human`, `builtin`, `script`. It states the tools (MCPs) it uses. | methodology |
| **WHAT** | **Domain** | What is being changed: node types, links, lifecycles, algorithms (`alm`, `organisation`, `platform`, ...). One domain per namespace; a type is referenced as `<namespace>@<NodeType>` (ADR 0012, 0013). The versioned graph is its content. | `domains/`, registry database (`domain_version`); each graph holds the published ones in memory (type catalogue) |
| **WITH WHAT** | **MCP, Connector, Adapter** | **MCP**: the generic usage of a tool by an LLM (`platform` namespace). **Connector**: the driver of a real service, a separate service that registers itself. **Adapter**: the code that implements the tools an MCP expects with the operations a connector exposes. It is an `AdapterDef` node of the `platform` namespace (usage `adapter`, template generated from the MCP and the connector), changed through a Change; a unit holds an *instance* with its parameter values (secrets as references), where organisation, MCP and connector converge (`Adapter` node, `organisation` namespace, owned by the unit: the owner of its version, ADR 0054). | graph + connector registry (MCP hub) |

Design rules that follow, to keep the whole consistent:

1. **Keep the concepts independent; couple only at the designated meeting points.** A methodology knows no
   organisation and no connector (it names MCPs; it references the types of domains, `alm@Requirement`). An MCP knows no connector
   and no adapter. A connector knows no MCP and no organisation. A domain knows no methodology. The **Adapter** is
   where organisation, MCP and connector meet; the **Assignment** (`organisation@Assignment`, ADR 0039) is where
   organisation and project meet, carrying the roles a unit or user locally holds on a project; the **Change** is
   where who, why, how and what meet at run time.
2. **Every modification is a Change.** No write to the graph outside one (the direct-write endpoints are for
   seeding and non-controlled nodes only), and every change names its intent (why), its holding unit (who), its
   methodology (how) and its namespace (what).
3. **Responsibility flows down the organisation.** Anything an organisation provides (adapters today, policies and
   quotas tomorrow) is resolved from the unit holding the change, then its ancestors, then `ORG-DEFAULT`: the nearest
   wins. Units share an MCP and a connector with different scopes (same file access, different root directory).
4. **What describes the enterprise is graph data, changed through changes** (organisation, adapters, MCPs,
   methodologies): versioned, reviewable, journaled. The exceptions: the domains, which define the graph itself (the
   registry versions them in its database, each graph holds them in memory, ADR 0023), service configuration and
   runtime registrations (a connector announcing itself and its liveness).
5. **What is available comes from who.** An action is schedulable only where the unit holding the change resolves the
   MCPs it declares (`mcps:`); an agent may declare MCPs for its llm / script actions. ABAC decides what a principal
   may do; adapters decide what the organisation can reach.
6. **Agents plan, actions execute.** An action does one thing; anything that needs a loop, a choice or planning is an
   agent over smaller actions.
7. **Library and instance.** Whatever is reusable across organisations is written once in the domain library (an
   algorithm with declared parameters, ADR 0018) and instantiated where it is used with parameter values: an adapter
   is a definition (`AdapterDef`), and each unit gives it its own scope (same adapter, another root directory).
8. **Adding a capability**: name the question it answers, put it in that concept, and cross concepts only at the
   meeting points above. Adding a real service is a new connector (a service that registers itself), never a change to
   the platform.

## Working notes

- A `go.work` of seven Go modules, one directory each (ADR 0125): `contracts` (`github.com/zimwip/goap/contracts`: the generated code `contracts/gen`, the pure model, `graphapi`), `lib` (shared libraries and service plumbing), `graph`, `engine`, `mcp`, `gateway`, and `platform` (every `cmd/*`, the services that are none of the others, `platform/e2e/*`). A package's import path is `github.com/zimwip/goap/<module>/<dir>`; a module may depend on contracts ← lib ← graph / engine / mcp / gateway ← platform only, each `go.mod` requiring exactly those (with `replace` to the sibling directories, so a module also builds with `GOWORK=off`); `platform/layering` `TestComponents` / `TestModuleRequirements` check it, tests included. `./...` at the root matches nothing: name the modules (`make` uses `$(PKGS)`, `./contracts/... ./lib/... …`); `make tidy` runs `go mod tidy` in each, `make lint` refuses an untidy one.
- Contracts: `proto/` → `make generate` (buf) → `contracts/gen/` and the web's TypeScript `web/src/gen` (`protoc-gen-es`, a dev dependency of the web, with the JSON forms `<Message>Json`; committed, never edit by hand). The web's API types (`web/src/lib/api/types`) are checked against them by `web/src/lib/api/contract.test.ts`: an interface named like a message carries its fields and only those (`ALIASES` for another name, `EXCEPTIONS` with the reason for a web-only field); a new type may be the generated `<Message>Json` itself. The protos keep no `reserved` fields: clients and services ship together and the database starts from zero, so a removed field simply goes.
- Tests: `make test`; PostgreSQL-backed tests (graph) run when `GOAP_TEST_PG_DSN` is set (`lib/pgtest`); SQLite variants always run.
- Storage has two SQL dialects: PostgreSQL (`migrations/`) and SQLite for the local mode (`migrations_sqlite/`, `make dev`, ADR 0010); the local mode writes through one connection and reads through a pool of read-only ones (`platform.OpenSQLiteReader`; the graph's transactions of a read-only context, `platform.ReadOnly`, a store's plain reads through its `Read` field; a graph test variant `sqlite-readers` runs every transaction there first, so a write in such a context must stay correct when run again on the writer; nothing that runs inside a graph transaction may wait on a lock held across a read of the graph, `graphsnap.View.Peek`; PostgreSQL likewise in `platform/cmd/graph`: `platform.PostgresReader`, a read-only pool, `Postgres.WithReader` runs those transactions with no `BEGIN` / `COMMIT`, a write (SQLSTATE 25006, a change or branch lock) runs again on the writer, test variant `postgres-readers`); schema changes go to both, and `TestSchemasAligned` (`lib/sqlschematest`, in `graph/graph`, `credsvc`, `mcpsvc`, `modelgw`, `prefssvc`, `domainsvc`) fails on any difference of tables, columns, defaults, keys, constraints or indexes (ADR 0074). A graph query both repositories run is written once in `graph/graph/sqlbuild.go` (`dialect` methods returning the text and arguments; a new query goes there, with its text per dialect in `sqlbuild_test.go`); what stays in `postgres.go` / `sqlite.go` is the executor, the scanning and the encodings. `make test-pg` runs every test against PostgreSQL (a throw-away `pgvector/pgvector:pg17` container unless `GOAP_TEST_PG_DSN` is set; there is no CI configuration in the repository, so run it before touching `postgres.go` or a `migrations/` file).
- End-to-end tests of the IDE (Playwright, `@playwright/test` pinned exactly in `web/package.json`): `web/e2e/*.e2e.ts` (vitest leaves them alone), `web/playwright.config.ts`; `make web-e2e` (`goap-local e2e`: the local stack on fresh data with the IDE and the demo data, then `npx playwright test`, then stop), `make web-e2e-run` against a running IDE (`GOAP_E2E_URL`, `GOAP_E2E_SUBJECT` / `GOAP_E2E_PASSWORD`); `E2E_ARGS` for Playwright; results and report in `.goap/e2e`. The shared steps live in `web/e2e/session.ts`; locate by role and label, wait on what the page shows.
- `make lint` must pass (go vet + gofmt + tidy `go.mod` files).
- `make.ps1` (and its `make.cmd` launcher) is the Windows twin of the `Makefile`: the same targets doing the same things (`dev` runs `goap-local -watch -web` on the binaries of `local-build`); change both together.
- Example methodologies use the domain of `domains/` (`alm`) and the built-in `organisation` and `platform` (loaded in tests with `methodology.LoadFile`). `methodologies/examples/` (`impact-analysis`, `test-design`) is exercised by `engine/methodology`, `engine/engine`, `platform/e2e/engine` and registry tests and is not seeded at start (the registry seeds the `*.yaml` directly under `methodologies/`); `methodologies/sdlc.yaml` (ALM domain, demo data of `platform/devseed`) by `platform/e2e/engine/sdlc_test.go`.

- Source components (ADR 0125): the engine and the graph meet only through the graph's contract, `contracts/graphapi` (requests, answers and errors of the operations on a change, `IsWorking`; imports `contracts/domain` only): `engine/engine` names no `graph/graph` type (write `graphapi.NodeCreate`, `graphapi.ErrConflict`), `graph/graph` keeps the names as aliases, `graph/graphsvc` names no engine type (its own `Publisher`, the `engine.GraphPort` check of its client is a test); `platform/layering` enforces it. A new request type of an operation the engine calls goes in `contracts/graphapi`. `graphapi.Port` is the graph as its callers see it (`engine.GraphPort` is an alias; the built-in MCPs call it too), `graphapi.NodeValidator` the plug of a graph-wide check; the client of the graph service is `lib/graphclient` (no `graphsvc` import outside the graph's compositions), the engine's telemetry `engine/enginetel` (`EngineTracer`, `LLMClient`, `JaegerTraces`): the gateway, the hub, the connectors, `lib/access` / `llmcfg` / `graphsnap` and `lib/telemetry` depend on neither the graph nor the engine (`platform/layering`). Domain converters of the protocol: `lib/domainpb`; `def.Record` / `def.Status` / `def.Latest` / `def.InForce` are the shared shapes. On a domain event (`goap.registry.domain.published` / `deleted`) the methodology registry runs `DomainsChanged` (cache dropped, `Recheck`): a published version that no longer compiles against the domains in force is **suspended** (`ErrSuspended`, `Service.Suspended`, proto `Methodology.suspended` / `MethodologySummary.suspended`, events `goap.registry.methodology.suspended` / `resumed`; nothing stored, recomputed from the domains of now; `Recheck` runs at start too): `MethodologyVersion` refuses it (no new change), `Methodology` refuses it (no run), `List` and the hub's listings leave it out; the web shows it in `DraftHeader`. The hub (`platform/cmd/mcp`) reads the domains through `domainclient` and the methodologies through the generated registry client (`builtin.Ports.Domains` / `Methodologies`), never compiled. The engine's tests (ADR 0125 §5): a test that runs the engine on a real graph goes in `platform/e2e/engine` (package `enginee2e`, its own `TestMain` registering the item types), reaching unexported workings through `engine.InternalsOf(e)` (add a method there rather than exporting the internal; production code never calls it); `engine/engine`'s own tests import no graph (`platform/layering` `TestTestLayering`). A test needing two modules goes in `platform/e2e/<name>` (package `<name>e2e`); the methodology registry, `platform/registrysvc`, stays in the platform for now.
- Concurrent writers (ADR 0127): the writers of one tree of changes are serialized by `Tx.LockChange` (PostgreSQL: advisory lock on the root change, read again once held; SQLite / memory: nothing to do), taken by `changeOpen` and `Graph.changeTx` before an operation reads what it checks, and by the guard at every write naming a change; a new operation on a change opens its transaction with `g.changeTx(ctx, id, ...)` (or `changeOpen`). `advanceBranch` takes `Tx.LockBranch` and moves the head only from the new commit's parent (`ErrConflict` otherwise; the head is the search of the branch's last commit, never written, two commits of a branch never share a parent: index `commit_parent`, ADR 0174 addendum); a merge reads and prepares everything first (the rebase onto the head it read, the branch taking the target's commits up to it, ADR 0177, the fast-forward's versions), what decides read again while the head moves, writing nothing (`checkFastForward`, `freshOnto`, `prepareAttempts`), the branch then takes the target's commits once, up to the head that stood (`finishFastForward`, `takeOnto`: rows, no commit; at the lock `reforkFastForward` takes what came since and keeps the plan when the head moved on none of its nodes), the nodes as the target will hold them read too (`targetHeads`), then locks its target for the writes only; a head moved at the lock has the plan read again, and a target moved on a node the branch changed (`errTargetMoved`) is rebased onto under the lock, then merged (ADR 0127 addendum). Lock order: tree, then branch. `concurrency_test.go` (meaningful under `make test-pg`).
- Versioning rule of the graph: outgoing links belong to the source node version (see `graph/graph/apply.go`), held as a link set (ADR 0141): its own rows, the set of an earlier version of the node as is (`node_version.links`), or its rows as a delta over one (`links_base`, `links_depth` at most `maxLinkDepth` 16, drop rows `link.removes`; skip deltas, addendum: `links_seq` the order of the set, the set of order k a delta over the one of order `k & (k-1)`, `baseSet`, a power of two whole); a writer goes through `Graph.putVersion` (`graph/graph/linkset.go`: `planLinks` before the version, its set given to `Tx.PutNode`, the rows after, `DropLink`; `LinkSetOf`; nothing is updated, ADR 0174 addendum), the reads compose the chain (`dialect.heldLinks`, `sqlLinksTo`: an entering link comes back once per version holding it); a hop of a navigation reads its link types only (`Tx.LinksFromOfType` / `LinksToOfType`, over the indexes `link_from (from_id, from_version, type)` / `link_to (to_id, to_version, type)`; a drop row carries the type of the link it drops; `BenchmarkNavigation`).
- Structures, bootstrap, guard (ADR 0054): a domain tags the node type building the organisation and the one building the projects (`structure: {kind, parent, root, selfParent, bootstrap}` on a node type: `bootstrap` gives the root's initial properties; one per kind across the domains, the built-in organisation domain tags `OrgUnit` / `ProjectUnit`; `TypeCatalog.Structure` / `IsA`, `Graph.Structure`; untyped graph: the catalogue of the built-in domains, `typecat.Builtin()`; ADR 0069: `graph/graph` and `contracts/domain` name no structure, no root key, `platform/layering` `TestCoreNamesNoStructure`; the constants of the built-in organisation are `access.DefaultOrg` / `DefaultProject` / `NodeTypeOrgUnit`..., for seeds and tests only). `Graph.Bootstrap` creates the roots the structures declare (`ORG-DEFAULT` and `PROJ-ROOT`) in one transaction and one applied change (services run it at start before any seed; `CreateChange` runs it too). `graph.New` wraps every repository transaction in the guard (`graph/graph/guard.go`): every node version / link / branch membership (`JoinCommits` takes a change) / node origin names an existing change, every version has a responsible unit (`Node.Responsible`, ADR 0161, a logical URL of the unit with no version, `lnk:<namespace>/<type>/<key>`, ADR 0154: a reference to a node is a link; `Graph.StructureURL` the canonical form, `Graph.StructureRef` reads a URL or a key; same for `Node.Project`, `Change.OwnerOrg` / `ProjectID`; what needs the key takes `.Key`, the web `refKey`; stamped from the previous version, else the change's unit; moved only by `NodeUpdate.Responsible` / `NodeEdit.Responsible`) and every node a project (`Node.Project`, the project's URL, the change's at its first version, never changes; ADR 0154 §9: keys, no foreign key, checked through `Graph.Directory` (`graph.StructureDirectory`, the platform's `access.Directory` in a content graph) when set, else in the transaction), every commit the result of a change (ADR 0056: the state before a namespace's first change is the empty commit id, `""`, which nothing stores; `Commit("")` / `BranchHead` read it), every change a unit and a project (`scopeChange`: the parent's, else the root unit for the unit; the project is never defaulted, a root change naming none is refused with `ErrInvalid`, ADR 0091), checked at the end of the transaction like deferred foreign keys; never bypass it (fixtures write through a change too, `seedNode`). The schema keeps no foreign key (the guard is the only check of the references: no trigger runs per row; `NOT NULL` columns and non-empty keys for owner and project stay; the schema started from zero, `0001_schema.sql`), and `Graph.AppendLog` refuses a change that does not exist. What the guard reads under the lock of a change it keeps for the transaction (ADR 0127): `lockedHead` reads the root, the header, the branch and the last position of its log in one statement, so a view kept whole is not read again, a branch or a commit header is read once (until a lock or a write of a branch), a unit or a project found is kept by the graph (`Caches.Structures`), a change created in the transaction is locked with no statement; a batch of checkouts appends its entries in one statement (`withEntries`, `Tx.AppendLogs`). There is no `organisation@owner` link: ownership is the version's owner (`SplitByOwner`, the adapters of a unit). The services reading the organisation (`lib/access`, `mcp/mcpsvc`) never name its types: they ask the graph for its structures (`Graph.Structures` / RPC `GetStructures`, `domain.Structures`: a list of structures with the types of each, `Organisation()` / `Project()`, a `User` being a unit; both structures live in one namespace, a platform constraint checked by `typecat`) and build their snapshots from them; the walk up a hierarchy is one resolver, `domain.Hierarchy` (`Structures.Hierarchy(kind, nodes, links)`, `Chain(key)`: self first, root last, cycle-safe), used by `access.Snapshot`, `mcpsvc.Snapshot` and the `goap-admin` listings (ADR 0068).
- Change lifecycle and gates (ADR 0058): a change may follow a domain lifecycle named by `Methodology.Lifecycle` (`Change.Lifecycle` / `State`, orthogonal to `ChangeStatus`; resolved through `graph.ChangeLifecycles`, implemented by `registrysvc.Service`, asked over RPC: ADR 0168, `registry.v1.ChangeGuardianService` served by the guardian service `platform/cmd/guardian` (port 8097, stateless, scaled with the graphs' load; the registry stores and validates only), `lib/guardianclient` plugged by `platform/cmd/graph`, `GOAP_GUARDIAN_URL`; the graph knows no methodology). `Graph.TransitionChange` checks the transition, `Graph.ChangeAuthorizer` (`change:transition`) and the CEL guard in the condition environment (`condition.CheckGuard`: `change`, `decisionPoints`, `world`); a gate is a guard requiring a decided decision point (`change.decision`, consumed by the move) and the `done` conditions of the steps of the state being left, no checklist of its own. A step is tied to a state by `pre: {"state:<name>": true}` (generated condition). The move is a `TypeTransition` fact (written only by `TransitionChange`); leaving a state freezes the impacts whose draft was started in it (the checkout and the edits refuse), going back sets later ones to `proposed`; the merge needs a final state (asked by `checkMerge`, ADR 0102), the commit does not. Keep the platform generic: states and gates are use-case level (domains, methodologies). `Graph.ChangeTransitions` (RPC `GetChangeTransitions`) judges each transition out of the state for the caller without taking it, every check that refuses listed (`TransitionBlock` kinds `status`, `permission`, `decision`, `guard`, `veto`, `objective`, `guardian`; the decided points its guard passes with, the reserve); `checkGate` / `checkGuardians` word their refusals from the same judgement (`gateBlock`, `guardianRefusal`). Web: the change tab lists the transitions out of the state with that judgement (`ChangeTransitions.svelte`, `web/src/lib/changeTransition.ts` `judgedOf`, `graph.transitionChange`), the lifecycle diagram draws them allowed or blocked over bundled rails (`LifecyclePreview.svelte`, `web/src/lib/lifecycleBundles.ts`) and the assistant has `transition_change` (write, no second dialog). Not yet: engine builtin, `sdlc` lifecycle.
- Commits and tags (ADR 0056): a commit is the state a change leaves (`Commit.ChangeID` mandatory), the first change of a namespace starts from the empty state (`CommitID ""`, `change.fork_commit` nullable); there is no `CreateCommit`; a tag names one node version (ADR 0143 §6: `domain.Tag{Node, Version}`, `Graph.TagVersion`, not unique, table `tag` with a foreign key to `node_version`; RPC `TagVersion`, `goap-change/tag`, `goap-graph/tags`, web `NodeTags.svelte` in the node's history), a smart tag a named set of versions in a store of its own (§7: `graph/smarttagsvc`, Connect `smarttag.v1.SmartTagService`, its own migrations on the graph's database, served by `platform/cmd/graph`, routed by the gateway; owner, shares `read` / `edit`, only the owner shares or deletes; no events). A change is applied in two steps: `CommitChange` validates it, writes the versions from its drafts (ADR 0079) and records it on its own branch as a commit of that branch (ADR 0175: one `committed` event per impact naming it; the change stays `active`, ADR 0102), `IntegrateChange` integrates it into the branch it forked from (`fast-forward`: joins; `merge`: a merge change with its own `committed` events; the change open, ADR 0166; conflicts leave it `committed`), `CloseChange` applies it; there is no `Apply` operation, port method or RPC: a caller commits, then merges or closes (only `Graph.CommitEdits`, the producer path, commits and closes, privately `apply`), and both answer a header, never a state: a caller that reads nodes asks for them. A root change is rebased onto the head of the branch it forked from before it commits (ADR 0101, at its merge since ADR 0102: `RebaseChange`, conflicts stop with `ErrConflict`, a clean rebase keeps the reviews), so commit is a fast-forward and the three-way merge only a race; commits record their `Kind` (`RebasedFrom` no longer written, ADR 0177). One commit and merge path (ADR 0102, `graph/graph/apply.go`, `rebase_committed.go`, `mergecheck.go`; no exception, whoever calls): `CommitChange` (a root change or a sub-change, ADR 0103) writes every accepted modification on the change's branch and reverts the nodes withdrawn since their commit (a version with reason `revert`, `domain.ReasonRevert`, holding the fork's value), then asks the guardian of the change in the same transaction (ADR 0146, `checkCommit`, `commitcheck.go`: `ChangeLifecycles.Commit` — the registry's activity goal, `decided` replaces the next — else the committable states, then the outer guardians; a refusal undoes the commit), never rebases, leaves the change `active` (`hasCommits`: an impact committed; `LandedCommit` only from a commit on a lasting branch), refuses `ErrNothingToCommit` (an `ErrInvalid`, carried over RPC by `rpcerr`'s reason header); a partial commit names its nodes (`CommitChangeRequest.nodes`, `Graph.CommitChangeNodes`: the accepted modifications and reverts of those nodes, an impact `via` one named following it; a node with nothing to commit `ErrInvalid`; - Pipelined writes and kept heads (`docs/architecture.md` *Pipelined writes*, *Kept heads*): on PostgreSQL a write transaction queues what nothing waits on (`BEGIN`, advisory locks, held inserts, the first log entry at the position the locked head reserved) and sends it with the next statement or the `COMMIT` (`graph/graph/pgpipe.go` `pipeTx`, `heldQuerier.write`); a new write whose answer is known beforehand is queued, a new append keeps the order (`takeNext` / `dropNext`). The head of a lasting branch its views read is held in memory and moved, never invalidated: by this graph's commits (the guard's `movedBranches` / `wroteHeads` / `headMoves`) and by the commit events of the other processes, which carry the header and, when `Whole`, every node moved (`Graph.FollowHeads` / `HeadEvent`, `heads.go`); a move not following the head held leaves it unknown; known 30 s with the events followed, else 1 s; the version of a node at the head is kept with it (`keptSelection`, else one statement: `CommittedAtKey`); the access directory stays apart (its own subscription). A write locks its change before it reads (`changeTx`), folds the facts it appends into the view (`guardTx.foldFact`) and leaves the versions it wrote in the version cache; a commit no guardian judges takes the light check (`Graph.judgesCommit`, `CommitJudge`: `guardianclient` judges a change scoped to an Activity only; *Reads a write skips*).
- One cache (ADR 0156): whatever a process keeps between calls is a `lib/cache` (`Cache[K, V]`, `Bounds{Bytes, TTL}`: estimated bytes by the size function given, an entry no one read for the TTL goes, the least recently read evicted first, a value larger than the cache not kept; `Update` for a read-and-write under its lock; estimates `cache.Of`, `WordBytes` / `SlotBytes` / `StructBytes`): the graph's views, version links, commit headers, impact validations (`Graph.Caches`, zero fields from `DefaultCaches`, read at each write), the compiled methodologies of the registry and its client (`registrysvc.CompiledBounds`), the compiled scripts of `lib/dsl`, the gateway's sessions. A new cache is one, with its bounds and a size function; the heads `graphsnap.Reader` follows are a state, not a cache.

- Counters of a change (ADR 0173): the commit records what each version does to its node over the impact's pre (`domain.EffectOf`: `created` / `modified` / `deleted` / `restored`, `requalified` from the `requalified` entry of ADR 0172, properties, state move, links added / removed / changed) on its `committed` event (`ImpactEvent.Effect` → `ChangeImpact.Effect` of the view; `recordInParent` the effect over the parent's pre, `effectOver`); `domain.StatsOf(impacts)` folds them, net per node, with the pending impacts by review; each commit and sub-change merge keeps `Stats.Committed()` on the header (`Change.Stats`, column `change.stats`, JSON in both dialects); graph statistics measure `changeCounters` (root changes); proto `Change.stats` (the fold when the impacts are answered, else the header) / `ChangeImpact.effect`; web `ChangeCounters.svelte`, `changeStats.ts`. - Change impacts are event-sourced (ADR 0029): every operation on them goes through `Graph.emit` (`graph/graph/impactevents.go`), which appends a `domain.ImpactEvent` to the log of the change and folds it into the view of the change; nothing else is stored for an impact: the version is its record (ADR 0174 and its addendum: no `change_impact` table; a version names its change, its impact and the entry of its change's log that committed it, `node_version.change_id` / `change_impact` / `log_seq` (a change commits several times; written with the version: the commit reserves the position of its committed entry first, `Tx.ReserveLogSeq`, then appends it there, `Graph.emitAt`, no `UPDATE`, held by the guard, `guardTx.reserved`; a revert names the impact withdrawn and the entry of its commit; a version is never rewritten when a branch takes it: the integration is the `branch_commit` row, its `change_id` and `log_seq` the entry of that change's log recording it, `VersionJoin.LogSeq`; by default nothing is updated), and what made it, its reviews, its `committed` event and effect, is read in the view of its change by that impact; `Tx.ChangeNodeIDs` the nodes a change wrote versions of; the changes acting on a node are read from the log, `change_log.node` of an impact entry of one event, `ImpactEvent.NodeID`; the graph tests replay every change's log against its view and check that each version names an impact of its change's log, `checkVersionImpacts`). A flow's view is `domain.ImpactsSeenBy`, a fold of the log. A payload leaves its envelope (id, change, impact, flow, execution, by, at, causation) to the columns of its log entry and a checkout of a stored version records the version only (`fromBase`, link ids `domain.BaseLinkID`), ADR 0142: read impact entries with `domain.ImpactEventsOf` (the graph: `decodeImpacts`, which hydrates the copies; the web: `decodeImpactEvents`), never by unmarshalling a payload: one entry carries the verdicts of a review or the versions of a commit (ADR 0144: `domain.SameEntry` events passed to one `Graph.emit` are one entry, `{"impacts": [...]}` with what they share hoisted; a review batch stages its verdicts, `Graph.stage` / `flush`), so emit the events of one commit or review together, by phase; a rebase is a `change.updated` entry, then per merged node a `checkedOut` of the committed version and an `updated` patch `domain.DraftDiff` (the diff of the merge), then the `graph.merge` review, then the commit (`installRebased`).
- A change is read as a view of its log (ADR 0153): one fold per change (`draftState`, `graph/graph/draftcache.go`) holds the impacts, drafts, conflicts, items, the impact events in log order, the phase of each impact and the position of each move, extended entry by entry (`foldEntries`) and by the writes themselves (`emitEntry`); a reader of any of these takes it from the view (`draftState`, `foldedEvents`, `draftsOf`, `st.phaseOf`), never from a read of the whole log; the view keeps its impacts in blocks and its maps in shards its copies share (`impactBlocks`, `cowMap`, `graph/graph/cowmap.go`: a write copies what it touches), and the impacts of a change are read through `c.Impacts()` (`domain.Impacts`: `All`, `At`, `Index`), never `c.Nodes`, which an operation's change sharing the view leaves empty (`ShareImpacts`), and an operation that wrote refreshes its work from it (`Graph.reread`), not by opening it again. A log facet (the history) is built for the call that reads it and kept for nothing else (stateless, `logEntries`): no cache of facets between calls. The views are kept between calls in a bounded cache (`draftCache`: `Graph.Caches.Drafts`, 64 MiB of estimated size, `draftState.bytes` counted by `apply` / `fact`, `approxsize.go`; 5 min without a read; a view from the cache is still brought up to the log). `Change.Seq` is the position a change was read at; a write notes the position it left a log at in the caller's watermark (`graphapi.WithWatermark`), a read may require one (`graphapi.AtLeast`, `ErrBehind`), over RPC `X-Goap-Change-Seq` / `X-Goap-At-Least` (`graphsvc.Handler.Positions`, `graphclient`; the web: `flux/positions.ts`, noted by the transport, `getChange` and the `change.updated` events, which carry the position of their write as `Change.Seq` / `Event.version`, asked of every graph request naming the change, a `behind` read retried); `Graph.ChangeAt` / `GetChange.at_seq` read a change as its log stood at a position. The guard reads change headers only (`ChangeHead`).

  drain), `credentials_outbox` (`goap.credentials.<subject>.registered` / `password_changed` / `session_started` /
  `session_ended`), `preferences_outbox` (`goap.preferences.<subject>.updated` with the keys, `reset`),

  `Emit(sink)` and the store writes take the messages; a composition runs each relay with `outbox.Start` (nil relay:
  no bus, no event). The methodology registry's facts are graph data: its events (`saved` / `published` / `deleted`)
  ride on the graph commit that stores them (`graphapi.Edits.Events`, `CarriedEvent`, proto
  `CommitEditsRequest.events`; a `system:` principal only, `GraphStore.commit` goes as `system:registry` for the
  person; `checkCarried` refuses the graph's own families), written after `change.applied`; `suspended` / `resumed` are
  published directly (recomputed). A new event of a service is written by its store in the transaction of its fact.
- Waiting at start (ADR 0169): a service needing another at its start tries once, then listens: `platform.Events.Await(ctx, subjects, try, retry)` tries again on an announcement, else after a doubling delay up to `platform.AwaitMaxDelay` (30 s, the fallback); a service others wait for announces itself once it listens, `platform.Server.Announce(events, subject)` (core NATS, outside the GOAP stream): `service.ready.domains` (`domains`), `service.ready.graph.platform` / `.content` (`graph`). Waiting: the graphs' type catalogue, the engine's, the registry's seed and `Recheck`, the guardian's `Recheck`. A new start-time dependency goes through `Await`.
- One event stream and presence (ADR 0053): `platform/eventsvc` (`Hub` is a `Publisher`/`EventSink` fed from NATS by `platform/cmd/events`; `Watch` resumes by `(epoch, seq)` or says `resync`; `Heartbeat`/`Leave` are the presence, in memory with a TTL). The graph publishes `change.updated` (`goap.changed.<id>`) for every change header / impact / log write, so a new write path needs no extra event. Web: never refetch after a write; `web/src/lib/flux/` (`events.svelte.ts` the one stream, `reducers.svelte.ts` events → `signals.svelte.ts` stamps; a view that loads depends on `stamp(keyOf.…)` in its `$effect`); every `rpc` carries `X-Goap-Command`.
