# GOAP — notes for contributors and agents

- **English is the project's official language.** All code, comments, docs, commit messages, and UI text must be in English.
- Architecture and concepts: `docs/architecture.md`. Keep it in sync with code changes.

## Mental model: who, why, how, what, with what

GOAP manages the whole scope of an enterprise. **Organisations work on the Domain to change it as their needs
require. The need is the intent of a Change; how they perform it is the Methodology; its actions say which tools
they use.** Every design decision starts by asking which of these questions it answers, and lives in that concept.

| Question | Concept | What it is | Where it lives |
|---|---|---|---|
| **WHO** | **Organisation** | Who acts, and the scope of responsibility. A hierarchy of units (`OrgUnit`, `part_of`); the default unit `ORG-DEFAULT` is the root of every unit. A unit holds changes, the adapters of its tools and its users; who may do what (`Policy` nodes, ADR 0020) lives here too; a user holds no role of its own but the `admin` flag, its roles are held on projects (ADR 0043). Mirrored by a hierarchy of **Project** (`ProjectUnit`, `project_part_of`, root `PROJ-ROOT`): what the organisation works on, identifying the methodologies that apply and so the roles they inherit (ADR 0035 §2, ADR 0039). A `Change` belongs to a project (`ProjectID`). | graph, `organisation` namespace |
| **WHY** | **Change** (intent) | The reason to act, and the blackboard of the execution: everything that modifies the graph goes through one. It has an intent, an owner unit, a methodology, and acts on one namespace. Agents and actions work on it. Pure questions about the world state need none. | `domain.Change` |
| **HOW** | **Methodology** | How a change is performed: goals, conditions, agents, actions, triggers. | graph, `methodology` namespace (`MethodologyVersion` + element nodes typed by the `methodology` meta-domain, ADR 0023) |
| ↳ | **Agent** | A broad task scope that needs planning and loops to be achieved (goap / utility / hybrid planner); may call sub-agents. | methodology |
| ↳ | **Action** | The smallest task, not splittable: preconditions, effects, cost. Kinds `llm`, `tool`, `human`, `builtin`, `script`. It states the tools (MCPs) it uses. | methodology |
| **WHAT** | **Domain** | What is being changed: node types, links, lifecycles, algorithms (`alm`, `organisation`, `platform`, ...). One domain per namespace; a type is referenced as `<namespace>@<NodeType>` (ADR 0012, 0013). The versioned graph is its content. | `domains/`, registry database (`domain_version`); each graph holds the published ones in memory (type catalogue) |
| **WITH WHAT** | **MCP, Connector, Adapter** | **MCP**: the generic usage of a tool by an LLM (`platform` namespace). **Connector**: the driver of a real service, a separate service that registers itself. **Adapter**: the code that implements the tools an MCP expects with the operations a connector exposes. It is an `AdapterDef` node of the `platform` namespace (usage `adapter`, template generated from the MCP and the connector), changed through a Change; a unit holds an *instance* with its parameter values (secrets as references), where organisation, MCP and connector converge (`Adapter` node, `organisation` namespace, owned by the unit: the owner of its version, ADR 0054). | graph + connector registry (MCP hub) |

Design rules that follow, to keep the whole consistent:

1. **Keep the concepts independent; couple only at the designated meeting points.** A methodology knows no
   organisation and no connector (it names MCPs; it references the types of domains, `alm@Requirement`). An MCP knows no connector
   and no adapter. A connector knows no MCP and no organisation. A domain knows no methodology. The **Adapter** is
   where organisation, MCP and connector meet; the **Assignment** (`organisation@Assignment`, ADR 0039) is where
   organisation and project meet, carrying the roles a unit or user locally holds on a project; the **Change** is
   where who, why, how and what meet at run time.
2. **Every modification is a Change.** No write to the graph outside one (the direct-write endpoints are for
   seeding and non-controlled nodes only), and every change names its intent (why), its holding unit (who), its
   methodology (how) and its namespace (what).
3. **Responsibility flows down the organisation.** Anything an organisation provides (adapters today, policies and
   quotas tomorrow) is resolved from the unit holding the change, then its ancestors, then `ORG-DEFAULT`: the nearest
   wins. Units share an MCP and a connector with different scopes (same file access, different root directory).
4. **What describes the enterprise is graph data, changed through changes** (organisation, adapters, MCPs,
   methodologies): versioned, reviewable, journaled. The exceptions: the domains, which define the graph itself (the
   registry versions them in its database, each graph holds them in memory, ADR 0023), service configuration and
   runtime registrations (a connector announcing itself and its liveness).
5. **What is available comes from who.** An action is schedulable only where the unit holding the change resolves the
   MCPs it declares (`mcps:`); an agent may declare MCPs for its llm / script actions. ABAC decides what a principal
   may do; adapters decide what the organisation can reach.
6. **Agents plan, actions execute.** An action does one thing; anything that needs a loop, a choice or planning is an
   agent over smaller actions.
7. **Library and instance.** Whatever is reusable across organisations is written once in the domain library (an
   algorithm with declared parameters, ADR 0018) and instantiated where it is used with parameter values: an adapter
   is a definition (`AdapterDef`), and each unit gives it its own scope (same adapter, another root directory).
8. **Adding a capability**: name the question it answers, put it in that concept, and cross concepts only at the
   meeting points above. Adding a real service is a new connector (a service that registers itself), never a change to
   the platform.

## Working notes

- Go module `github.com/zimwip/goap`; core logic in `pkg/` (no infra deps), services in `internal/` + `cmd/`.
- Contracts: `proto/` → `make generate` (buf) → `gen/` (committed, never edit by hand).
- Tests: `make test`; PostgreSQL-backed tests (graph) run when `GOAP_TEST_PG_DSN` is set (`internal/pgtest`); SQLite variants always run.
- Storage has two SQL dialects: PostgreSQL (`migrations/`) and SQLite for the local mode (`migrations_sqlite/`, `make devlocal`, ADR 0010); schema changes go to both.
- `make lint` must pass (go vet + gofmt).
- Example methodologies use the domain of `domains/` (`alm`) and the built-in `organisation` and `platform` (loaded in tests with `methodology.LoadFile`). `methodologies/examples/` (`impact-analysis`, `test-design`) is exercised by `pkg/methodology`, `pkg/engine` and registry tests and is not seeded at start (the registry seeds the `*.yaml` directly under `methodologies/`); `methodologies/sdlc.yaml` (ALM domain, seeded by `internal/graphsvc/seed.go`) by `pkg/engine/sdlc_test.go`.
- Versioning rule of the graph: outgoing links belong to the source node version (see `pkg/graph/apply.go`).
- Structures, bootstrap, guard (ADR 0054): a domain tags the node type building the organisation and the one building the projects (`structure: {kind, parent, root}` on a node type; one per kind across the domains, the built-in organisation domain tags `OrgUnit` / `ProjectUnit`; `TypeCatalog.Structure` / `IsA`, `Graph.Structure`; untyped graph: `domain.BuiltinStructures`). `Graph.Bootstrap` creates `ORG-DEFAULT` and `PROJ-ROOT` in one transaction and one applied change (services run it at start before any seed; `CreateChange` runs it too). `graph.New` wraps every repository transaction in the guard (`pkg/graph/guard.go`): every node version / link / branch membership (`JoinBranch` takes a change) / node origin names an existing change, every version has an owner unit (`Node.Owner`, stamped from the previous version, else the change's unit; moved only by `NodeWrite.Owner` / `NodeEdit.Owner`) and every node a project (`Node.Project`, the change's, never changes), every baseline the result of a change (ADR 0056: the state before a namespace's first change is the empty baseline id, `""`, which nothing stores; `Baseline("")` / `BranchHead` read it), every change a unit and a project (`scopeChange`: the parent's, else the root unit / the default project, the `ProjectUnit` flagged `default`), checked at the end of the transaction like deferred foreign keys; never bypass it (fixtures write through a change too, `seedNode`). The schema repeats it (`NOT NULL` foreign keys, deferred for the bootstrap; the schema started from zero, `0001_schema.sql`). There is no `organisation@owner` link: ownership is the version's owner (`SplitByOwner`, the adapters of a unit). The services reading the organisation (`pkg/access`, `internal/mcpsvc`) never name its types: they ask the graph for its structures (`Graph.Structures` / RPC `GetStructures`, `domain.Structures` with the types of each, a `User` being a unit; both structures live in one namespace) and build their snapshots from them.
- Baselines and tags (ADR 0056): a baseline is the state a change leaves (`Baseline.ChangeID` mandatory), the first change of a namespace starts from the empty state (`BaselineID ""`, `change.baseline_id` nullable); a name is a `domain.Tag` on the change that left the state (`Graph.TagChange`, not unique: several changes may carry one name); there is no `CreateBaseline`. A change is applied in two steps: `CommitChange` validates it and records its state on its own branch (baseline `Kind` `commit`, one `landed` event per impact, status `committed`), `IntegrateChange` integrates it into the branch it forked from (`fast-forward`: joins; `merge`: a merge change with its own `landed` events; status `applied`; conflicts leave it `committed`, the former `merge_pending`); `Apply` is both. A change is its branch (given at commit when it has none). A baseline's state is derived from what its change did (`landed` events, or the versions joined for a fast-forward), so only every `MaterializeEvery`-th baseline of a chain stores its entries (`Baseline.Gap` 0, `GOAP_MATERIALIZE_EVERY`, 1: all) and the others are a header, replayed and cached by the guard (`pkg/graph/state.go`; reads through the guard always hold the nodes, `Graph.Materialize` stores one). Run the suites with `GOAP_MATERIALIZE_EVERY=1`, `3` and `100000` after touching baselines: `checkStates` replays every baseline. `Apply`'s `baselineName` tags the change when it differs from its title.
- Versions and branches (ADR 0032): `node_version.branch` is the branch a version was written on and never changes; a merge that lands a version as is makes it join the target (`Tx.JoinBranch`, `node_branch`), only a node changed on both sides gets a merge version. Ask "is it on branch X" with `LatestOn` / `Node.On`, not the label. Baselines are stored as deltas from their parent with checkpoints (`pkg/graph/baselinedelta.go`); callers still pass and get whole maps.
- Options (ADR 0009 §3, ADR 0032 §6): an option is a flow opened as a hypothesis (`pkg/graph/option.go`); the change's active option is where every graph call that names no flow goes (`Change.ResolveFlow` at the public entry points: `AddNodes`, `WriteNode`, `ReviewNodeOn`, `AddItems`, `BlackboardIn`, `ValidateBoard`, `ChangeView`, `ChangeGraph`); `domain.MainFlow` ("main") names the main flow explicitly, internal code keeps passing "" for it.
- Decision points (ADR 0009 §4): facts of the main flow (`domain.KindDecisionPoint` + `DecisionEvent`, replayed by `Change.DecisionPointsAt(now)`), written only through `Graph.OpenDecision` / `RuleDecision` / `AnswerQuestion` / `RatifyDecision` (`AddItems` refuses the kind); actions reach them through items of kind `decisionPoint` (`pkg/engine/decisions.go`) and the builtin `decision.investigate`. Conditions see `options`, `activeOption`, `decisionPoints`, `questions`; the platform conditions (`condition.Platform`: `open_questions`, `no_decision_pending`...) are added to every compiled methodology unless it declares the name.
- Authorization is ABAC (Casbin) via `authz.Authorizer`; the rules are `Policy` nodes and the callers `User` nodes of the `organisation` namespace, read by `pkg/access` (compiled-in defaults `pkg/authz/casbin.go` seed them and apply while the graph has none; administrators are never locked out). There is no IAM service.
- Project (ADR 0039): `organisation@ProjectUnit` mirrors `OrgUnit`'s hierarchy (`project_part_of`; root `PROJ-ROOT`, `domain.DefaultProject`, self-linked rather than rootless like `ORG-DEFAULT`), naming the methodologies that apply to it. `organisation@Assignment` is the meeting point of organisation and project (`assigns_org` to an `OrgUnit` — `User` is a subtype of `OrgUnit` so it satisfies this too — `assigns_project` to a `ProjectUnit`), carrying the roles a unit or user locally holds there; `pkg/access.Snapshot.ProjectChain`/`ProjectRoles` resolve them, merged into the subject's roles by `access.Authorizer.Authorize` when `authz.Resource.ProjectID` is set (`pkg/engine` threads `Process.Project` into `stepAllowed`'s check). `domain.Change.ProjectID` names the project a change acts in, resolved and stored by `CreateChange` (ADR 0054: the parent's, else the default project); `Methodology.Administrative` / `Change.Administrative` mark organisation/project/policy/adapter-management changes. `methodology@Role` is a materialized element node like `Agent`/`Action` (ADR 0023, `internal/registrysvc/defs.go`'s `defKinds`). A user is created automatically, the same node as its ADR 0037 personal unit (`USR:<subject>`, `internal/graphsvc.EnsureUser`, called by the `EnsureCaller` interceptor on every authenticated call and by `resolveOwner`'s `@me` path). The active project is a JWT claim (`X-Goap-Project`, `POST /auth/dev-token/project` reissues it) and a web header selector; the left nav is one "People & Organisation" entry sub-navigated into Organisation/Projects/Users, Assignment reached from any of the three via an action or a context menu (`AssignmentsPane.svelte`). Not implemented: OrgUnit-side action restriction on a project.
- User bootstrap, mandatory parenting, local auth (ADR 0040): `EnsureUser` resolves `ORG-DEFAULT` *before* creating anything (the graph is bootstrapped before serving, ADR 0054; creating the `User` first would leave a permanently broken one — no `member_of`, no admin — if the root were missing, and defeat the first-admin bootstrap for everyone after), then links the new user `member_of` it and, when it is the first `User` node the namespace has ever held, grants it `admin` through a platform Assignment created in the same commit (ADR 0046, 0047; `access.PlatformAssignmentKey`, linked by `ToKey` to the `User` node being created in the same edit), checked with `g.NodesOfType` against *live* state (`tx.LatestNodes`), not a baseline snapshot (a benign race can only grant admin to more than one subject, never to none). `pkg/graph.Commit` refuses to create an `OrgUnit`/`ProjectUnit`/`User` without exactly one `part_of`/`project_part_of`/`member_of` link, except `ORG-DEFAULT`/`PROJ-ROOT` themselves (`checkRequiredParent`, checked against the edit's own declared links before anything is written); `checkParentInvariant` additionally re-reads a *modified* node's actual live links right after the write, since a client (e.g. the "move" action, `graphEdit.moveNodeItem`, "Move to…" on the Organisation/User tabs) can work off a `headGraph` baseline snapshot that predates an import-written link and so not know one already exists — refusing a resulting second link rather than silently leaving two. A third gateway `AuthMode`, `"local"` (verifies tokens the same way `"hs256"` does), backs `POST /auth/register`/`/auth/login`/`/auth/logout` with `internal/credsvc` (shaped like `internal/prefssvc`: its own store/migrations, a bcrypt hash per subject, never graph data; its `Store` interface is meant to move to `platform.Secrets`/Vault later). `GET /api/auth/config` tells the web which sign-in UI to show; `Signin.svelte` replaces the shell with no token in local mode; `UserTab.svelte`'s "Log out" action hides itself once a real SSO mode exists (not yet implemented, along with server-side token revocation).
- Sign-in by default, waiting unit (ADR 0042): `"local"` is the default `AuthMode` (`gateway.DefaultAuthMode`; `GOAP_AUTH_MODE=none` for the fixed dev principal, `hs256` when tokens come from elsewhere); `goap-dev` generates its JWT secret when none is set (`.goap/jwt_secret`). `gateway.Config.OnSignIn` declares the user at register/login (`graphsvc.EnsureUser` in process, `graphsvc.Client.DeclareUser` from the gateway) then `access.Directory.Refresh`. `EnsureUser` now commits the `User` + `member_of` as one change on main (no more import write; serialized per process, retried on `ErrConflict`). New users join the waiting unit, an `OrgUnit` an administrator creates and flags `waiting` at their discretion (`access.PropWaitingUnit`, `graphsvc.NewUserUnit`; none flagged: `ORG-DEFAULT`; smallest key if several); admins set it at unit creation (Organisation explorer) or on the Organisation tab ("Make waiting unit" moves the flag in one change, "Clear"). The header's user menu has "My profile" and "Log out" (local mode; `signsInLocally` in `web/src/lib/stores/auth.svelte.ts`).
- Front location and session (ADR 0052): the active tab is the URL path and query (`web/src/lib/shell/router.ts`, `startRouting` in `tabs.svelte.ts`); tabs, project, explorer state are not in `localStorage`; the project is the token claim; a sign-in/out (token appears/disappears, any tab) clears per-user storage and reloads on home (`stores/auth.svelte.ts`, `restartOnSessionChange`); a 401 ends the session in every auth mode.
- Keeping a session (ADR 0044): `POST /auth/refresh` (local) reissues a valid token (`gateway.Config.TokenTTL` / `GOAP_TOKEN_TTL`, 12h), keeping identity and `auth_time`, up to `MaxSession` / `GOAP_SESSION_MAX` (7 days); token endpoints answer `{token, expiresAt}`; 401s say `token expired` / `invalid token`. The web's `stores/auth.svelte.ts` (local mode) refreshes a quarter of the lifetime before expiry, re-checks on visibility/focus, follows other tabs, and ends the session (`endSession`, notice shown by `Signin.svelte`) on an expired token or a 401 for the current token (`api.reportUnauthorized`, called by `rpc`, `whoAmI`, the event stream).
- Server-side sessions (ADR 0045): register/login open a session in `internal/credsvc` (`auth_session`, both dialects; `Service.StartSession` / `SessionActive` / `EndSession` / `EndSessions`, Connect `credentials.v1`; `SetPassword` ends the subject's sessions); tokens carry its id (`sid`, kept by refresh and project switch). The gateway's authenticator refuses an ended session (401 `session ended`) through a cache shared with the endpoints (`gateway.Prepare`, `Config.SessionCheckTTL` 15s; refresh checks afresh; 503 when an unchecked session cannot be checked); a token without `sid` is refused in local mode. `POST /auth/logout` (`{"everywhere": true}`) ends the session(s); the web's profile menu has "Log out on every device".
- Project-scoped roles (ADR 0043; administration itself became a platform role in ADR 0047, superseding this ADR's "admin is a flag" decision — see below): every role a user holds is granted by an `Assignment`, a project-scoped one holding a methodology's (`methodology@Role`), needed by a project through its applicable methodologies (inherited by sub-projects); `access.Authorizer.Authorize` merges the roles of the subject's chain (`Snapshot.SubjectChain`: `USR:<subject>`, its unit, ancestors) on the resource's project chain (root project when none) into `r.sub.Roles`, for every request. Default policies (`authz.DefaultPolicies`; `LegacyDefaultPolicies` upgraded by `graphsvc.SeedAccess`): admin everything, `onProject(r.sub)` for process/object/node/tool/change-apply, `mayRun(r.sub, r.obj)` for `action:run`, `agent:run`, `model:use` (`r.obj.Roles`); methodologies, domains, triggers, organisation, policies, adapters are admin-only. Agents and actions declare `roles: [...]` (checked against the methodology's roles; trigger roles are not); the engine checks them (`Engine.runRoles` / `mayRun` / `checkAgentRoles`; an action the initiator may not run waits for an `action:run` approval, a human one for a submitter holding the role) and acts as `Engine.actor` (initiator on the process's project). Resources thread `ProjectID` (enginesvc, graphsvc `CreateObject`, transitions, mcpsvc tool calls, modelgw). Web: `web/src/lib/projectRoles.ts` (roles a project needs, who holds them), Project tab, Assignments pane role picker.
- Platform roles, administration migrated (ADR 0046, 0047): a fixed, built-in catalog of the platform namespace (`platform@Role`, `pkg/mcp.BuiltinRoles`: "admin", "reader"; kept in sync with the code by `SeedBuiltins` the way the built-in MCPs are, ADR 0028) granted by an `organisation@Assignment` naming no project (`assigns_org` only, key `access.PlatformAssignmentKey`); `access.RoleAdmin`/`RoleReader` name them for the ABAC rules, `access.PlatformRoles` lists the grantable names. `Snapshot.PlatformRoles` resolves it over the org chain; `Snapshot.Enrich` merges it in unconditionally (resource-independent, so `Authorizer.Floor()`, which calls only `Enrich`, sees a platform-granted admin too — no stored policy can lock one out, ADR 0020/0043), alongside the project-scoped roles `Authorize` adds for the request's resource. `access.User.Admin` (`admin: true`) is now read-only back-compat for a node written before ADR 0047 (`UserFromProps`/`Enrich` still honor it); new code (the ADR 0040 first-admin bootstrap, `graphsvc.createUser`) grants admin through the platform Assignment instead, never the flag. Fixes the dead end of a project naming no methodology: it declared no role, so no Assignment could target it; a platform role reaches it anyway. Web: `AssignmentsPane.svelte`'s project selector offers "platform-wide (no project)", listing `web/src/lib/projectRoles.ts`'s `PLATFORM_ROLES` (a static mirror, not yet read live from the `platform@Role` nodes); the User tab's admin checkbox still edits the legacy flag, not yet migrated to the Assignment.
- Attributes (ADR 0055): a node type or link type defines its properties as `Attribute`s (code, label, type, widget, enum, default, section, order, tooltip, `asName`, and the `property_validator` instances plugged on it; a bare name is shorthand), resolved by the type catalogue (ancestors first, overridable by name); a domain declares `enums`; node types plug `node_validator` instances. The graph checks the type / enum membership of values on commit; the web renders and edits nodes from them (`web/src/lib/attributes.ts`, `AttributeEditor.svelte`, `NodeTypeTab` / `LinkTypeTab` / `EnumTab` / `LifecycleTab`: one tab per domain object).
- Node types (ADR 0012, 0013): a node's type is composite, `<namespace>@<NodeType>` (one domain per namespace: `alm`, ...; shipped with the code and frozen, `domains/builtin/`: the meta-domain `methodology`, `organisation` and `platform`; a new namespace is a new domain); every type or link type reference is qualified. The registry is the reference of the types (published domains); the graph and the engine keep an in-memory type catalogue loaded from it at startup and synced by its events (lifecycle, validators, search, editor, `extends`), and the graph refuses an unknown type. Nothing is projected onto the graph.
- Methodologies are graph nodes (ADR 0023): a version node (`MV:`) and one node per element typed by the meta-domain (`methodology@Agent`, ...), kept by `registrysvc.GraphStore`. Domains are the definition of a graph, not graph data: the registry keeps them in its database (`registrysvc.SQLDomainStore`, `internal/registrysvc/migrations*/`). YAML is import/export only.
- Processes (ADR 0034): a methodology's `processes` are trees of steps (sub-steps, `action`, alternative `actions`, `agent`, nested `process`, or manual) sequenced by their conditions only (never by position), with `references` to their reference documents, compiled by `pkg/methodology/process.go` into an agent + goal per process and one action per step (named by its path); agent, nested-process and method steps run through the builtin `process.step` (`pkg/engine/steps.go`) as sub-agents on the same change. Methods (ADR 0035, reshaped by ADR 0050, `pkg/methodology/method.go`) are references, never actors, and name no agent: a method owns `actions` (a pool its steps inherit) and/or `steps`, with `done`, `planner`, `model`, `mcps`; compiling it generates an agent of its name (`Agent.Role` = its responsible role) run as a fresh sub-agent per step; a step naming a capability (`method:`) runs the applicable method (priority, then the most specific `when`, `Method.Specificity`), once per element of its `foreach` CEL list (`groupBy`: per group) in parallel streams with `vars.item` bound (`pkg/engine/foreach.go`, `Lane` in the progress). `Engine.Progress` (`pkg/engine/progress.go`) is the read model of a run's process. Roles (ADR 0035 §2): a methodology declares `roles`, steps and methods assign them RACI style; users hold them on projects through Assignments (ADR 0043; a token may still carry one unscoped or per unit, `role@UNIT`, `authz.Principal.HasRoleIn` + `Resource.OrgChain`); `step:perform` / `step:approve` are checked by the engine.
- Compilation issues guide the user (`pkg/methodology/issues.go`): `Compile` refuses a methodology with issues, `CompileLenient` builds what stands and returns the issues with it, each `Issue.Activity` tied to the process, method or step it is about (`Methodology.ActivityOf`); `GetProcessGraph` / `CheckLevels` use it, so the flow of a draft with broken rules is drawn as far as it stands (`DraftFlow` → `ProcessFlowView` marks the steps, lists the rules in its panel) and the Issues console and the editors' fields keep pointing at the definition path.
- A condition is never both an input and an output of an action or a step, whatever the values (ADR 0051, `overlap` in `pkg/methodology/methodology.go`): no `pre: {x: false}` guard next to `effects: {x: true}`; the planners never repeat an action whose effects already hold. The compiler refuses it, tied to the step (`Issue.Activity`), and the flow draws it red (`GapNoop`).
- Agents (goap/utility/hybrid planners) and script actions (JS via goja, Go via yaegi) use the DSL in `pkg/dsl` (docs/dsl.md); scripts run in sandboxes (`internal/sandbox`, `GOAP_SANDBOX`).
- Algorithms (ADR 0018): the DSL is tied to a usage (`pkg/algo`, `pkg/dsl/algo.go`); domains declare algorithms + instances that node types (validators) and lifecycle transitions (guards, actions) plug; the type catalogue (the graph's copy of the registry's model) resolves them and the graph runs them (`pkg/graph/algorithms.go`). Only domains carry them.
- Node index (ADR 0026): node types declare `search` properties (`pkg/methodology`); `Graph.Observe` publishes `NodeEvent` / `BaselineEvent` after each commit (`pkg/graph/events.go`); `pkg/index` holds the stores (memory, SQLite FTS5, PostgreSQL pgvector — schema changes go to `pkg/index/migrations*/`), `internal/indexersvc` + `cmd/indexer` the service; `goap-dev` runs it in process. PostgreSQL index tests need pgvector (`pgvector/pgvector:pg17` with `GOAP_TEST_PG_DSN`).
- Composition links: a link type flagged `compose: true` says its target is a part of its source (`defines`, `sub_activity` of the `methodology` domain); the methodology editor derives its panes and step trees from the type catalogue (`TypeCatalog.sectionsOf` / `partsOf`), only binding a type to its draft collection in `TYPE_COLLECTION` (`web/src/lib/views/editors/methodologyTabs.ts`).
- Node editors (ADR 0027): a node type names the IDE editor of its nodes (`editor`, inherited through `extends`); the web opens a node only through `openNode` (`web/src/lib/nodeEditors.ts`), editors are registered with `registerNodeEditor` (`web/src/lib/views/nodeEditors.ts`), unknown or empty: the default node editor.
- Built-in MCPs (ADR 0028): `goap-graph`, `goap-change`, `goap-scheduler`, `goap-admin` (`pkg/mcp/builtin.go`), served by the connectors of `internal/connectors/builtin` inside the hub, acting for the caller; `graphsvc.SeedBuiltins` gives them to every unit through `ORG-DEFAULT`. An MCP has a `scope` (`action`, `agent`: declared on agents only and reached by their llm actions, as `goap-scheduler`; `both` by default), enforced by the engine host and scheduling and checked by the registry. An `organisation@Adapter` node restricts an MCP (`disabled`, `tools`, `deny`, `readOnly`); restrictions add up along the unit chain (`mcp.Restriction`).
- Telemetry: `internal/telemetry` (OpenTelemetry); keep span / attribute names stable (docs/architecture.md §3.7).
- Change impacts are event-sourced (ADR 0029): every operation on them goes through `Graph.emit` (`pkg/graph/impactevents.go`), which appends a `domain.ImpactEvent` to the log of the change and updates the `change_impact` projection; never call `Tx.PutChangeImpact` elsewhere (the graph tests replay every change's log against the projection). A flow's view is `domain.ImpactsSeenBy`, a fold of the log.
- One log per change (ADR 0030): facts, journal records and impact events are entries of `change_log` (one order, `seq`), with `type` (`fact.*`, `journal.*`, `impact.*`), `flow`, `process_id`, `execution`, `subject` as columns to filter on; write and read them through `pkg/graph/changelog.go` (`Tx.AppendLog` / `Tx.Log`), `ListChangeLog` serves the filtered log.
- Risks and actions (ADR 0036): items of kind `risk` / `action`, each a version of the record of its `data.key`; `Change.Risks` / `ActionItems` fold the register (`pkg/domain/risk.go`), CEL `risks` / `actions` and platform conditions. `pkg/brief` renders the compact brief every LLM action on a change gets and `goap-change/brief`, `trace`.
- Transverse methodologies (ADR 0036 §3): `appliesTo: [<methodology>]` + `on: [{event, filter}]` run their processes alongside the changes of those methodologies, choreographed by events (`step.completed` is published for every process step): one companion run per change and process, re-run in place per event with `vars.event`, an inbox for events arriving while it works; a process whose goal no plan reaches **waits** (`waiting`, `HumanTask` kind `condition` with its `conditions`) when what is missing is established outside it (no action of its agent produces it and assuming it the goal is reachable, `pkg/engine/awaiting.go`), else it is **stuck** (not terminal: it carries a task `unblock`); both are retried when the change moves (`pkg/engine/companion.go`), and a person who answers for the run can always unblock it (`Engine.Unblock`, `pkg/engine/unblock.go`: waive conditions through a `waiver` item of the change, applied to that run only; retry; abandon). No namespace of their own. `methodologies/risk-management.yaml` applies to `sdlc`, whose release needs `risks_under_control`.
- Personal changes and preferences (ADR 0037): a change held by a personal unit (`USR:<subject>`, `owner_org: "@me"`) belongs to its subject only (`graphsvc.Handler.PersonalScope`, `domain.Change.Personal`); a change that landed nothing is purged with its log by `Graph.PurgeChange` (`Tx.DeleteChange`, RPC `DeleteChange`; `Graph.PurgePolicy` lets a rule keep it); the settings dialog of the web stages every edit of the platform (platform or organisation nodes) as impacts of such a change (`web/src/lib/stores/pending.svelte.ts`; `settings.svelte.ts`: Save = accept + apply, Discard / leaving = purge; `llmEdit.ts` lays the staged nodes over the gateway lists and lists / reviews the alias proposals).
- User preferences (ADR 0038) are not graph data: the `preferences` service (`internal/prefssvc`, `cmd/preferences`, Connect `preferences.v1`, `prefssvc.Schema` lists the keys it accepts) keeps one document per subject, read and written by that user only and saved as they change it (`web/src/lib/stores/preferences.svelte.ts`); the user is declared in the graph, what they like is not.
- Execution journal (ADR 0011): the engine records ticks / actions / approvals on the change (`domain.ExecutionRecord`); items carry `execution`. The observer (`methodologies/methodology-improvement.yaml`, `pkg/observe`) turns runs into change impacts on the definition nodes of a methodology draft.
- `web/src/lib/help/dsl.md` is a copy of `docs/dsl.md` (the web dev container only mounts `web/`); `make lint` checks they are identical.
- Svelte 5 rune state modules (`*.svelte.ts`) must not share a base name with a component (`*.svelte`) in the same directory (e.g. `searchOverlay.svelte.ts` next to `SearchOverlay.svelte`): on case-insensitive filesystems (Windows, default macOS), an extensionless import of the state module (`from './foo.svelte'`) resolves to the component file instead, since Vite tries an exact match before extending to `.svelte.ts`. This builds fine on case-sensitive Linux CI and only breaks locally on Windows/macOS. Either name the pair distinctly or always import the state module with its full extension (`from './foo.svelte.ts'`).
- One event stream and presence (ADR 0053): `internal/eventsvc` (`Hub` is a `Publisher`/`EventSink` fed in process by `goap-dev`, from NATS by `cmd/events`; `Watch` resumes by `(epoch, seq)` or says `resync`; `Heartbeat`/`Leave` are the presence, in memory with a TTL). The graph publishes `change.updated` (`goap.changed.<id>`) for every change header / impact / log write, so a new write path needs no extra event. Web: never refetch after a write; `web/src/lib/flux/` (`events.svelte.ts` the one stream, `reducers.svelte.ts` events → `signals.svelte.ts` stamps; a view that loads depends on `stamp(keyOf.…)` in its `$effect`); every `rpc` carries `X-Goap-Command`.
