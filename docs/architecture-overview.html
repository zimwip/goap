GOAP architecture

Seven Go modules in one go.work, deployed as a dozen services behind one gateway. Organisations change the graph through changes; the engine runs the methodology that says how.

Logical: modules and who may depend on whom

Units of code and build, not of deployment. Each module is a directory at the repository root with its own go.mod; imports go downward only, and platform/layering checks every import, tests included, and each go.mod. A binary assembles several modules.

Physical: services at run time

The compose stack: each box is a container running one binary, platform/cmd/<name>, with its host port. Boxes take the colour of the module whose service they run; every call is connect-rpc, and every service's events go over NATS JetStream: each service writes them in an outbox table in the transaction of their fact, and its relay publishes them (ADR 0136).

connect-rpc callevent over NATSnot drawn: preferences and credentials (called by the gateway only), the MCP hub calling the graph and engine for the built-in MCPs, the events the hub, the gateway, the preferences and the credentials publish through their outboxes

One step of a change, end to end

  1. The person starts a step. The IDE calls StartProcess; the gateway checks the token and the active project, then forwards.
    gateway → engine
  2. The engine loads how. It asks the registry for the methodology version the change follows, compiled against the domains in force (refused if suspended).
    engine → registry
  3. It reads the blackboard. Change, nodes, items, decision points and history come from the graph through graphapi.Port; conditions are evaluated on it and the planner picks the next action.
    engine → graph
  4. The action runs. An llm action goes through the model gateway (one ledger row per call); a tool action through the MCP hub, which resolves the unit's adapter and calls the connector (the Claude coding agent's sessions calling the model back through the gateway's /anthropic endpoint, a ledger row per call); a script in the sandbox.
    engine → modelgw · mcp hub → connector
  5. The result commits on the change. Impacts become drafts and items on the change log; nothing is a version until review, commit and merge.
    engine → graph
  6. Everyone sees it. The graph writes change.updated in its outbox with the fact, and its relay publishes it; the event stream pushes it to every open IDE, the indexer reindexes, and companion runs react.
    graph ⇢ NATS ⇢ events · indexer · engine

make dev: one process

goap-dev composes every service in process on SQLite (.goap/goap.db): no NATS, no Docker. Air rebuilds it on each Go change and Vite serves the IDE.

make dev               # :5173 IDE, :8080 API
.\make.ps1 dev         # Windows

Working in the go.work

  • ./... at the root matches nothing: make test, make lint name the modules.
  • make tidy after changing imports; lint refuses an untidy go.mod.
  • A test that needs two modules goes in platform/e2e/<name>.
  • Each module also builds alone: GOWORK=off go build ./....
