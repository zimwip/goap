# ADR 0120 — The references of a methodology are links of the graph

**Status**: accepted, implemented · **Date**: 2026-10 · Builds on ADR 0023 (definitions in the graph), ADR 0034
(processes), ADR 0035 (methods, roles), ADR 0109 (conditions derived from the context) · Amends ADR 0023

## Context

ADR 0023 stores a methodology version as graph data: a `methodology@MethodologyVersion` node and one node per element
(`Condition`, `Action`, `Goal`, `Agent`, `Process`, `Method`, `Role`, and, since the Activity concept, one `Step` /
`MethodStep` node per step), tied to the version by `defines`. But the elements referred to each other by **name, in
their properties**: an action's `pre` and `effects` were maps of condition names, an agent's `actions` and `goals`
lists of names, a step's `action`, `process` and RACI `roles` names, a process kept the JSON of all its steps although
each step was a node of its own. The graph held the nodes and almost none of their relations: nothing in it said that
the condition `framed` is the output of the action `frame` and the input of the step `analysis`, a reader of the graph
(the baseline explorer, the index, a query, the self-observation) had to parse JSON to find it, and an element nothing
used (a condition no activity needs nor produces, a role nobody holds) went unnoticed. The `Activity` type even
declared a `goals` attribute no code wrote: what an activity reaches is its output conditions.

Question answered (CLAUDE.md, rule 8): **HOW** (the methodology, as graph data).

## Decision

### 1. A reference to an element of the version is a link

The definition (YAML, the registry API, the web editor) keeps naming its elements. The registry's store
(`registrysvc.GraphStore`) cuts every name that resolves to an element of the version out of the properties and
writes it as a link of the built-in meta-domain `methodology` (1.11.0); reading the version puts the names back. One
table drives both directions (`pkg/methodology/refs.go`, `refFields`: `EncodeRefs` / `DecodeRefs`):

| Link | From → to | Fields (definition) | Attributes |
|---|---|---|---|
| `requires` | Action, Goal, Step → Condition | an action's `pre`, a goal's `pre`, a step's `pre` (`input` on its node) | `value` |
| `produces` | Action, Method, Step → Condition | an action's `effects`, a method's `done`, a step's `done` (`output`) | `value` |
| `uses` | Agent, Method → Action | `actions` | `position` |
| `pursues` | Agent → Goal | `goals` | `position` |
| `performed_by` | Step → Action | `action` (as `action`), `actions` (as `alternative`) | `as`, `position` |
| `nests` | Step → Process | `process` | |
| `assigns` | Agent, Action, Step, Method → Role | `roles` (as `run`), an agent's `role` (`actsAs`), RACI (`responsible`, `accountable`, `consulted`, `informed`) | `as`, `position` |
| `aggregates` | Condition → Condition | `all` / `any` / `none` (as the quantifier) | `as` |
| `specializes` | Action → Action | `specializes` | |
| `main_goal` | MethodologyVersion → Goal or Process | the version's `goal` | |

So a condition is one node, the output of the activities that produce it and the input of those that require it,
with the value each one asks for on the link.

A name that resolves to no element of the version **stays in the property**: a condition of a library (`imports`) or
generated by the platform (`state:x`, `step:p/s`, `pending:a`), an element of another methodology (`m/x`), a name a
draft does not declare yet. It has no node to link to. Those attributes stay declared on the types (strict attributes),
their descriptions say they only hold such names. The `goals` attribute of `Activity` is removed; `Process` and
`Method` lose `steps`: a step is a node of its own, reached through `sub_activity` only, its order its `position`.

### 2. Derived links

Some references are kept in the definition's own words and only shown by the graph, never read back
(`methodology.DerivedRefs`, `registrysvc.capabilityLinks`):
- `mentions` (any element or the version → Condition): a condition a CEL expression of the element reads
  (`conditions.x`, `self.conditions.x` in a `where`, an `expr`, a filter) or a nested structure names (the
  conditions of an assessment state, the `until` of a persistent agent);
- `assigns` / `pursues` as `trigger`: the roles and the goal of a trigger of an agent;
- `carried_out_by` (Step → Method): the methods whose `for` is the capability a step names.

### 3. Versions of the links

A link reaches the version of its target it was written against (ADR 0003): editing an element gives its node a new
version and leaves the references to it in place, suspect. They are references all the same: the store reads a
version with its suspect links (`withSuspects`, `Graph.SuspectLinks`, `graphsvc.Client.BaselineGraphWithSuspects`),
as does the cascade of the activities of a sub-change (`activityWithin`). A save brings the links of every node to the
definition: a link it no longer makes is removed, one whose attributes changed is replaced (`Graph.Commit` no longer
skips a link whose type and target exist when its attributes differ or the edit removes it), an element leaving the
definition drops its links.

### 4. No element stands alone

By default no element of a methodology exists alone: each is linked to another element of the version (a link of its
own, or one reaching it), or names something outside it (a library condition, another methodology). This is a
principle of modelling, not a rule of the graph: nothing checks it, no issue or warning reports it, and a methodology
of a single element saves, publishes and runs. The shipped methodologies had three dead conditions (`release-based` 0.1.1, `methodology-improvement`
1.5.1, `sdlc` 0.8.2 drop them).

### 5. The self-observation writes links

The proposals of the self-observation (`pkg/observe`) stay in the terms of the definition; `selfimprove` writes them
on the definition nodes in the terms of the graph (`graphWrite`: the names of elements are links, the links of the
fields a proposal sets replace those of the node) and reads the accepted ones back the same way (`definitionProps`),
so a proposed specialization is a `specializes` link and removing an action from an agent removes its `uses` link.
A link written by a DSL node operation may carry attributes (`NodeOpLink.Props`).

## Consequences

- The graph of the `methodology` namespace says what the methodology does: from a condition, the activities producing
  and requiring it; from a role, what it is assigned; the baseline explorer and any graph query read it without
  parsing JSON.
- A dead element is visible in the graph (a node with no link), but nothing refuses or flags it.
- The definition, the registry API, YAML import / export and the web editor are unchanged; the stored form of a
  version changes. A version stored before reads back as it was (its names are properties, which `DecodeRefs` keeps);
  its next save writes the links.
