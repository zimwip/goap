# ADR 0163 — The graph service in Rust, behind a comparing proxy

**Status**: accepted; phase 1 implemented (the workspace, the store, the proxy, the perf targets), phase 2 implemented (the reads of the bench, the shadow mode), phase 3 implemented (the writes of the bench), phase 4 under way (the smart tags, the reads of the domain registry) · **Date**: 2026-10

## Context

The graph service carries the load of the platform: every change, every commit and every read of a view goes through
it. The performance phases shaped it with a set of choices, each measured by `make perf`:

- **What a commit reads.** A baseline stores only its header; its state is a selection of the last commit of each node
  on its branch up to its order (ADR 0140, 0143). A commit and a merge read only the nodes they touch, in batches
  (ADR 0137 and addendum: `prefetch`, `BaselineVersions`, `LinkSetsOf`). The N+1 reads of a page are batched
  (`NodesAt`, change heads).
- **Links.** A version's links are a link set held as skip deltas of depth at most 16 (ADR 0141), written in batches
  of a thousand; a navigation hop reads its link types only, entering links by source.
- **Reads.** A request that only reads runs on a read-only pool, with no `BEGIN` / `COMMIT` on PostgreSQL, and runs
  again on the writer when it meets a write (SQLSTATE 25006, SQLITE_READONLY). `GetNode` answers a page of links.
- **Changes.** A change is a fold of its log (ADR 0153), its impact events carrying what they change (ADR 0142), one
  log entry per review or landing (ADR 0144); positions travel as watermarks (`X-Goap-Change-Seq`,
  `X-Goap-At-Least`).
- **Caches.** One bounded cache kind (ADR 0156): drafts 64 MiB, version links 32 MiB, headers 4 MiB, validations
  16 MiB, five minutes without a read.
- **Writers.** The writers of a tree of changes are serialized by an advisory lock on its root, then the branch lock
  (ADR 0127); the guardians judge in the transaction of the commit (ADR 0140).
- **Contracts.** Every read names its view (ADR 0157), reach filters it (ADR 0161), events leave through an outbox
  (ADR 0136).

Go reached the point where the remaining costs are the allocations of the folds and the decoding of the rows. Rust
removes the garbage collector from the hot paths and lets the type system carry invariants the Go code checks at run
time. The rewrite must not be a translation: only the behaviour of the RPCs and endpoints must stay the same.

## Decision

1. **A Cargo workspace beside the Go modules**, `rust/` (not in the `go.work`), generated from the same `proto/`:
   - `goap-proto`: the messages (prost, with pbjson for the protobuf JSON form) and per service a table of its methods,
     a server trait whose every method answers `unimplemented` by default, its router and its client, generated by
     `build.rs` with protox (no `protoc`); the descriptor set is exposed for the proxy.
   - `goap-connect`, `goap-ctx`: the Connect protocol (unary and server streaming, proto and JSON codecs, the error
     model, interceptors) over axum and reqwest.
   - `graph-store`: PostgreSQL (tokio-postgres, deadpool) or SQLite (rusqlite, compiled in: the one C of the build).
     Both keep a writer and a pool of read-only connections; `StoreError::is_read_only` sends a read that met a write
     to the writer. The migrations are the Go services' own files (graph, domain registry, smart tags), embedded and
     recorded in the same `schema_migrations` table (PostgreSQL by name under the advisory lock of the schema, SQLite
     by component and name), so either service starts on a database the other wrote.
   - `graph-service`: the binary `goap-graph-rs`, serving `GraphService`, `DomainService`, `SmartTagService` and
     `ImportService` with the environment of the Go service (`GOAP_HTTP_ADDR`, `GOAP_DB_DSN`, else
     `GOAP_SQLITE_PATH`, else a database in memory), `/healthz` and `/readyz`.
   - `goap-proxy` (below).
   The pure core (`graph-core`: views, folds, selection, link sets, the guard's obligations) comes with phase 2, free
   of I/O; the store is a trait per dialect with the SQL text of each, a reader and a write transaction as distinct
   types (a write cannot be asked of a reader), the tree lock a token the write operations take, the caches `moka`
   with the bounds of ADR 0156, the impact events one enum serialized to the bytes Go writes.
   Cypher reuses an existing parser (`decypher`, else `uni-cypher`); the scripts of the domains run on `boa` (no C)
   behind a `ScriptEngine` trait, a precompiled path (QuickJS as WebAssembly) left for later.
2. **A proxy in front of the graph services, deployed on its own**: `goap-proxy`, a Connect proxy that reads any method
   of `proto/` through the descriptors (no code per method). `GOAP_PROXY_MODE`:
   - `go`, `rust`: every call to one service, bytes passed as they are;
   - `split`: every call to the Rust service, replayed on the Go one when it answers `unimplemented` (HTTP 501, or a
     route it does not know): the two share one database. `/proxy/coverage` lists the methods called, who served them
     and those that still fall back; `POST /proxy/probe` asks the Rust service each method of the four services with
     an empty request (a test or perf environment only);
   - `compare`: every call to the Go service, which answers the client, and to the Rust one, each on its own database,
     one call at a time. Each side allocates its own UUIDs, so the proxy pairs the ids found at the same place of the
     two answers (lists matched by what their elements hold once the unknown ids and the times are blanked, map keys
     that are ids likewise; a short id, the eight first digits of a UUID as in `change-3013a15b`, follows its UUID),
     writes the Go ids of the next requests (body and headers) as their Rust twins, reads the Rust answer back in Go
     ids, masks the times and the fields of `GOAP_PROXY_IGNORE`, and gives a verdict: `same`, `order_differs`,
     `message_differs` (the soft ones), `differs`, `error_differs`, `undecodable`, `rust_unimplemented`. Every call is
     a line of `calls.jsonl` (verdict, both durations, differences, the ids that clash with an earlier pair, the bodies
     of a divergent call) in `GOAP_PROXY_REPORT_DIR`; `/proxy/report` writes `summary.json` and `ids.json`.
   - `shadow`: every call to the Go service, which answers the client; a call that only reads (the Go rule of
     `ReadOnlyRequests`: `Get…`, `List…`, `Export…`, `Diff…`, `Search…`, `Compare…`, `Is…`, `Query…`, a stream
     left out) goes to the Rust one too, both on one database, one call at a time: the Rust reads are judged against
     what the Go service wrote before the Rust service writes anything. No id to pair: the verdicts and the report
     are those of `compare`.
   - `goap-proxy diff-db --go <dsn> --rust <dsn> --ids ids.json` compares the tables of the two databases as
     multisets, once the ids are paired (the comparison's, then the rows one of a kind on each side) and the times
     masked.
   `/metrics` counts the calls per method and who served them (`goap_proxy_calls_total{service,method,served_by}`),
   the verdicts and the time of each side.
3. **The performance stack goes through the proxy.** `make perf` (mode go, `PERF_PROXY=0` without it), `make
   perf-rust` (`deploy/compose/perf.rust.yml`, mode `PERF_RUST_MODE`: split until the Rust service serves every
   method, then rust), `make perf-diff` (mode `PERF_DIFF_MODE`: `shadow` while the Rust service only reads, both on
   the schema `graph`; `compare` once it writes: both schemas dropped, the Go service on `graph`, the Rust one on
   `graph_rs`, then `diff-db`; goap-bench serial and seeded, then the report; `PERF_DIFF_RUST=go` compares Go with
   Go).
   The image `goap/rust:dev` (`docker build --target rust`) holds both Rust binaries.
4. **Phases, one pull request each**: (1) the workspace, the store and its migrations, the skeleton service, the
   proxy, the targets; (2) the reads (views, `GetNode`, neighbourhoods, baselines, listings, queries); (3) the writes
   of the bench (changes, impacts, review, commit, merge, rebase, the domain registry); (4) everything else, then the
   Go service and the split mode leave the stack. Each phase is done when `make perf-diff` finds no divergence on what
   it serves.

## Consequences

- The comparison is measured before it measures Rust: Go against Go (`PERF_DIFF_RUST=go`) on 939 calls of the bench in
  lifecycle mode gave no divergence and no clashing id, and `diff-db` found the fourteen tables of the two databases
  the same. Lists the graph orders by id come in another order on each side: `order_differs` is soft.
- Both services read and write one schema; a migration lands in the Go directories and the Rust service embeds it on
  its next build. `TestSchemasAligned` keeps the two dialects aligned as before.
- The Rust service holds the same multi-database option as the Go one (PostgreSQL, SQLite); the Go service goes away at
  the end of phase 4, the proxy stays as the entry of the performance stack and of later comparisons.
- Phase 2 (the reads). `graph-core` holds the reads as functions over a store trait (`store::ReadTx`, one statement
  or a few batched per method): the selection of a state (ADR 0143: the chain of forks, batches of 2000, the node
  list of the namespace for a whole state), the view of a branch, a node with its entering links from the version of
  each source the view holds, the neighbourhood (suspect links), the pages (links by type, nodes by type and text),
  the versions of a node, the headers of the changes and their pages (`changes_page`, `node_changes`), the lineage gap
  of two baselines and their difference (`lineage_gap`, `diff_baselines`). `graph-store` writes the SQL of both
  dialects once (`read/sql.rs`, as `sqlbuild.go`) and reads the rows into one value shape. `goap-graph-rs` serves
  `GetNode`, `ListNodeLinks`, `GetNodeNeighbourhood`, `ListBaselineNodes`, `ListNodeVersions`, `GetBranch`,
  `DiffBaselines`, `ListChanges` (headers) and `ListNodeChanges` for a platform service acting by itself (no reach);
  it answers `unimplemented`, so the Go service answers in mode split, a person or a service acting for one (the
  reach and the access snapshot of ADR 0161), a view of a change (the fold of its log, ADR 0153), a read at a log
  position (`X-Goap-At-Least`), the state of a change's branch, a change read whole, a unit or project named by its
  key (the structures of the catalogue). Those reads, `QueryView` (Cypher) and the other listings move to phases 3
  and 4.
- Measured in mode shadow, goap-bench serial and seeded: on PostgreSQL (lifecycle, 4000 versions) 1,528 reads of five
  node reads, then (commit, 5000 versions) 1,455 reads of the eight methods the bench reads with, all `same`
  (`ListNodeLinks`, which the bench never calls, is covered by the tests only); on SQLite (goap-dev
  and `goap-graph-rs` on one file, lifecycle, 2000 versions) 794 reads, all `same`. One fix came out of it: a float
  read from `jsonb` differed at its last digit until serde_json parsed floats correctly rounded (`float_roundtrip`),
  as Go does. The Rust service answered each read in less time than the Go one (GetNode p50 3.7 ms against 9.0 ms,
  GetBranch 1.1 against 6.6), a hint only: it reads second, after the Go service warmed the database's pages.
- Phase 3 (the writes of the bench). `graph-core` `write/` runs a write in one transaction of the store (`Tx`: the
  change logs folded once per change, the guard's obligations, the outbox, the positions the logs were left at for
  `X-Goap-Change-Seq`): `ImportDomain` (a new version a platform service imports, `graph-catalog` `imported`: the YAML
  read strictly, checked as `Domain.Validate` and the type catalogue check it, stored with Go's JSON of the definition
  and its `domain_outbox` event; a domain with issues, lifecycles, algorithms, validators, forms, documents or
  structures, a version already stored, or anything yaml.v3 reads more loosely is the Go service's), `CreateChange` / `DeleteChange`, the impact operations (create, checkout and its batch, update,
  link create / delete), `ImpactNodeReviewBatch` (the record of the review first, then every verdict in one entry
  naming it as its cause, ADR 0105), `CommitChange` (the versions, their link sets shared or as deltas, ADR 0141, one
  `committed` entry), `MergeChange` (a fast-forward), `CommitEdits` (the producer's path, all of it in one
  transaction), `ListDomains`, and `GetNode` / `ListNodeLinks` in the view of a change (its fork, its commits, its
  drafts). It serves the simple world: a platform service acting by itself, the main flow, a log of impact events and
  review records only, no sub-change, lifecycle, guardian, personal change, platform namespace, planned creation,
  URL target, domain running validators, revert, rebase or three-way merge, no dependency; anything else answers
  `unimplemented` with its transaction rolled back, and the split proxy replays it on Go. Measured in mode compare
  with Rust behind a split proxy (Go on the Rust schema for what it does not serve), goap-bench serial and seeded on
  PostgreSQL: lifecycle and commit (200 changes, new domain versions on the way) give no divergence and nothing falls
  back, the outbox events are the same but for the order of a baseline's `set` map, and `diff-db` finds the tables
  the same but for the order a link id decides (the `drafted` of a checkout, the order `CommitEdits` writes its edits
  in), which Go against Go shows as well.
  The proxy pairs the ids of two answers by place, and of two lists by what their elements hold; elements alike but
  for ids not paired yet (two new links between new nodes, each side in the order of its own ids) say nothing of
  which is which, so they are left unpaired, compared as ids, until an answer tells them apart (pairing them by
  position mispaired them half the time, and every call after diverged).
- Phase 4 (everything else), under way. `SmartTagService` is served whole (`graph-service` `smarttags.rs`, the SQL in
  `graph-store` `read/smarttags.rs`: the times `timestamptz` on PostgreSQL, Go's RFC 3339 text on SQLite), for any
  caller, its errors worded as Go words them; the proxy pairs its ids (32 hex digits) like UUIDs. Driven through the
  compare proxy (create, share, update, list, get, delete, the refusals), every call is `same`, messages included.
  `GetDomain` answers the built-in domains (their YAML read as `def.ParseDomain` reads it) and the stored ones
  (`graph-service` `domainpb.rs`: the definition mapped onto `registry.v1.Domain` as `lib/domainpb` maps it);
  `ExportDomain` the JSON of a stored domain as Go writes it (the definition through YAML and back: empty lists
  written, empty `requires` and forms dropped, keys sorted, Go's indentation, `gojson::to_string_indent`); the YAML
  export and the built-in domains are still Go's. Every built-in, `alm`, `code` and a bench domain, the unknown
  format and the missing domain: `same`. `ListTypes` resolves the catalogue of the domains in force (`Catalog::types` /
  `link_types`, the node validators of each type, a transition's `requires` and `children`). A platform service's
  `PublishDomain` (of a draft with nothing the Go service alone checks), `CreateDomainVersion` (the stored JSON under
  the new number, Go's text kept on SQLite) and `DeleteDomain` (a draft removed, a published version archived) write
  as the Go service does, with the event of each in `domain_outbox`. A scenario of 26 calls (each refusal included):
  every one `same`, served by Rust, the tables and the outbox of the registry the same. `SaveDomain` and
  `ValidateDomain` read the edited domain from the protocol as `DomainFromPB` does (`domainpb::imported`); a draft
  with issues stays Go's, which stores it and words them. Reading the definitions Go writes, a nil slice is a `null`

  The reads of the catalogue (`IsAdminOnlyType`, `ListItemTypes` with the item types this service gives a meaning,
  `graph-core` `items`, `GetStructures`) and `ListNamespaces` are served for any identified caller, as Go serves them;
  but the first call of a person creates its user (Go's `EnsureCaller`), so a person the graph holds no user of yet
  is left to Go (`Graph::identified`), which creates it in the shared database. `GetChange` answers the whole
  change as `ChangeChecked` does (`graph-core` `write::whole`): the header, the impacts of the fold, the items of its
  facts, its position and, for an open change, the check of each main-flow draft against what a version must satisfy
  (`valid`, the message, `modified` against the version checked out from); a draft with origins and a read at a
  position (`at_seq`) are still Go's. A scenario of 41 calls (checkout, edit, refusals, a change not found, a
